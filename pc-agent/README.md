# PC-OFF 설치형 프로그램 (Windows) — Phase 2

근무시간이 끝나면 직원 PC 화면을 잠그는 프로그램. 웹앱(`../webapp`)이 Phase 1에서 열어둔
API 4개(`/api/agent/{pair,policy,events,overtime}`)만 사용하며 **웹앱 코드는 건드리지 않는다.**

- 지시서: [../docs/04_architecture/PC-OFF-개발지시서-2026-07-26.md](../docs/04_architecture/PC-OFF-개발지시서-2026-07-26.md) §5
- 기술: .NET 10 + WPF (외부 라이브러리 **0개** — 통신·JSON·암호보관 모두 윈도우/닷넷 기본 기능)

---

## 실행 방법 (사장님)

`PC-OFF_실행.bat` 더블클릭 → 빌드 후 자동 실행.
프로그램은 창이 아니라 **화면 오른쪽 아래 트레이(숨겨진 아이콘 `^`)** 에 파란 전원 아이콘으로 들어간다.

| 트레이 오른쪽 클릭 메뉴 | 하는 일 |
|---|---|
| 연결 설정... | 서버 주소·컴퓨터 이름 입력, 웹에서 받은 **6자리 연결코드**로 연결 |
| 서버 연결 확인 | 지금 회사 설정(퇴근시각·유예·일시사용·휴일·승인된 연장근무)을 받아와 보여준다 |
| 수집하는 정보 | 근로자 고지 화면 — **무엇을 보내고 무엇을 안 보내는지** |
| 종료 | 프로그램 종료 (⚠️ **잠금 시간에는 막힌다** — 아래 참조) |

**연결 순서**: 웹 로그인 → [계정] → "내 PC 연결" → [연결코드 발급] → 나온 6자리를 이 프로그램에 입력.

### 실제로 잠기는지 확인할 때 — `PC-OFF_테스트실행.bat` (2-C 추가)

평소 실행(`PC-OFF_실행.bat`)은 **잠금 시간대가 되면 화면을 덮고 그 시간이 끝날 때까지 안 풀린다.**
확인만 하고 싶을 때는 **`PC-OFF_테스트실행.bat`** 을 쓴다. 안전장치가 함께 켜진다:

| 안전장치 | 내용 |
|---|---|
| 60초 자동 해제 | 잠금화면이 **스스로** 풀린다(갇히지 않는다). 남은 초가 화면에 표시된다 |
| 자동 잠금 1회 | 그 뒤로는 **저절로 다시 잠기지 않는다**. 없으면 새벽에 켠 PC가 "덮기→풀기"를 되풀이해 못 쓰게 된다 |
| 미리보기 메뉴 | 트레이에 **[테스트] 잠금화면 미리보기** 가 생겨, 잠길 시각을 기다리지 않고 원할 때 확인할 수 있다 |
| 종료 허용 | 테스트 모드에서는 잠금 중에도 트레이 [종료]가 동작한다 |

⚠️ 테스트 모드는 **실행 인자(`--test-mode`)로만** 켜진다. 설정 파일(`config.json`)에 두면 직원이
메모장으로 고쳐 잠금을 영구히 무력화할 수 있기 때문이다(2-A 검수 치명 지적). 자동 시작 등록에도 넣지 않는다.

### 잠금화면에서 직원이 할 수 있는 일

| 버튼 | 하는 일 |
|---|---|
| 연장근무 신청 | 지금부터 종료 시각(30분 단위)을 골라 신청. **웹 신청과 같은 결재선**으로 들어가고, 관리자가 승인하면 **1분 안에 자동으로 풀린다** |
| 일시사용 | 회사가 정한 시간(기본 30분)만큼 잠깐 푼다. 사유는 **목록에서 고르기만** 한다(직접 적는 칸 없음). 횟수는 **서버가 센다** |
| 서버 다시 확인 | 지금 곧바로 회사 설정을 다시 받아온다 |

## 지켜야 하는 규칙 (사규)

1. **비밀값 평문 금지** — 기기 토큰을 로그·화면·예외 메시지에 절대 쓰지 않는다. 서버는 해시만 갖는다.
2. **수집 범위 확장 금지** — 화면캡처·키로깅·앱 목록·이석 측정은 지시서 §0에서 **범위 밖**. `PolicyModels.cs`에 없는 항목을 늘리려면 먼저 보고한다.
3. **fail-open** — 정책을 못 받았으면 **잠그지 않는다**. 확신이 없을 때 잠그는 쪽으로 기울지 않는다.
4. **웹앱 무접촉** — `../webapp` 파일을 고쳐야 하는 상황이 오면 멈추고 보고한다.
5. **자유입력 금지** — 일시사용 사유는 회사가 정한 목록에서 고르기만 한다(민감정보 유입 차단).

### 오프라인 동작 (2026-07-27, 앱 0.4.0 · 사장님 결정 A·B)

- 서버가 근무일 정보를 **오늘부터 31일치** 준다 → 인터넷이 끊겨도 **한 달간 규칙대로 잠긴다**
  (이전에는 이틀치만 받아 3일째부터 잠금이 사라졌다 = 랜선만 뽑으면 풀리는 구멍).
- 인터넷이 끊긴 동안에는 **[일시사용] 한도가 따로** 열린다(기본 하루 6회 = 30분 × 6 = 3시간).
  인터넷이 없으면 [연장근무 신청]을 보낼 수 없어, 그대로 두면 외근 직원이 다음 근무일까지 갇히기 때문이다.
  - 실제 횟수 = `max(회사 하루 횟수, min(6, 180분 ÷ 1회 길이))`. **회사가 0회로 꺼 두면 오프라인에서도 0회.**
  - 이 값은 **서버가 정책에 실어 내려준다**(`tempUse.offlinePerDay`). 앱에 같은 숫자를 적어 두지 않는다.
- 그때 쓴 것은 `temp_use_offline`으로 기록되어 [PC관리]에 **일시사용(오프라인)**으로 구분돼 남는다.
  서버의 "오늘 쓴 횟수"는 온라인분만 세므로 **금요일 밤 사용분이 월요일 몫을 깎지 않는다**.
- **한도 우회 차단**: 서버가 오프라인 사용 횟수를 **일어난 시각 기준**으로 함께 세고(`offlineUsedToday`),
  앱은 서버 값과 자기 값 중 **큰 쪽**을 쓴다. 랜선을 뽑았다 꽂고 앱을 껐다 켜도 한도가 되살아나지 않는다.
- **오프라인 판정**은 "서버에 닿지도 못했다(HTTP 상태 0)"일 때만이다. 401·5xx는 서버가 대답한 것이므로
  오프라인이 아니다 — 사무실에서 누른 일시사용이 "오프라인 사용"으로 기록되면 안 되기 때문이다.
- ⚠️ **배포 순서: 서버(webapp) 먼저 → 앱.** 반대로 하면 앱이 옛 서버에 새 기록 종류를 보낼 수 있는데,
  그때는 앱이 스스로 옛 방식으로 돌아가도록 막아 두었다(서버가 오프라인 한도를 안 주면 새 종류를 쓰지 않는다).

### 2-D에서 반드시 확인할 것 (2-C 검수가 "실기기 확인 필요"로 남긴 것)

1. 🔴 **가상 데스크톱**(Win+Ctrl+D로 새 바탕화면 / Win+Ctrl+←→ / Win+Tab) — **Win+D와 같은 급의 우회 경로**다.
   지금의 자가치유(`RestoreIfMinimized`)는 최소화·숨김·최상위 해제만 되돌리므로 **가상 데스크톱은 못 막을 수 있다.**
   (Win+D·Win+M은 2-C에서 실기기로 막히는 것을 확인했다)
2. **혼합 배율 다중 모니터** — 노트북 150% + 외부 모니터 100%처럼 배율이 다른 조합에서 **덮이지 않는 자리**가 생기는지.
   생기면 그 자리가 그대로 우회 경로가 된다. (같은 배율 두 대는 2-C에서 확인 완료)
3. **잠금 중 윈도우 종료·로그오프** — `Window_Closing`이 닫기를 막고 1초마다 `Show()`를 다시 하므로 OS 종료가 지연되는지.
4. **UAC 승격 창·전체화면 프로그램**과의 앞뒤 순서 다툼.
5. 시나리오 4종(정상 퇴근 / 연장근무 승인 해제 / 일시사용 / 오프라인 복구)을 **처음부터 끝까지** 한 번에.
6. **오프라인 보완(0.4.0) 실기기 확인** — 랜선(또는 와이파이)을 끄고: ①잠금이 그대로 걸리는가
   ②[일시사용]이 "인터넷이 끊긴 동안 6회" 문구로 열리는가 ③다시 연결하면 쌓인 기록이 올라가고
   [PC관리]에 **일시사용(오프라인)**으로 보이는가 ④그 뒤 앱을 껐다 켜도 오프라인 횟수가 **되살아나지 않는가**
   (서버가 세어 준 값을 앱이 받아 쓰는지 확인하는 항목이다).

## 판정 규칙 (사장님 결정 2026-07-26 — 코드: `Core/LockDecider.cs`)

```
사용 가능 = 근무일 ∧ 출근시각 ≤ 지금 < 퇴근시각 + 유예
          ∨ 승인된 연장근무 시간대
          ∨ [일시사용] 중
그 외 전부 = 잠금
```
- **출근 기준시각 전에도 잠근다** → 규칙이 "근무일 09:00~18:10만 사용" 한 문장으로 끝나고, 조기출근 과로도 함께 막힌다.
- **주말·공휴일은 온종일 잠근다** → 휴일근무 지시 없이 일하는 것을 막는다. 필요하면 연장근무 승인이나 [일시사용]으로 푼다.
- **확신이 없으면 잠그지 않는다**(fail-open). 정책 모름 / 오늘 날짜 정보 없음 / 어제 유예가 새벽으로 넘어온 구간.
- 시간대는 **한국 시간(+09:00) 고정**(`Core/Hm.cs` `CompanyOffset`). 서버가 시각을 UTC(`Z`)로 보내므로
  표기에서 시간대를 읽으면 판정이 9시간 어긋난다(2-B 실기기 검증에서 실제로 잡은 버그).

## 2-B에서 지킨 것 (2-A 검수에서 나온 약속) — ✅ 이행 확인

1. ✅ **정책 캐시를 암호화해 보관**한다(`Core/PolicyCache.cs`, DPAPI, 자물쇠는 토큰과 **다른 값**).
   [수집하는 정보] 화면이 근로자에게 "암호화해 보관합니다"라고 고지했으므로 평문이면 **허위 고지**가 된다.
2. ✅ **시각 비교는 분(정수)으로만** 한다(`Core/Hm.cs`). `"9:00"`과 `"10:00"`은 글자로 비교하면 뒤집힌다.
3. ✅ **정책 값 검증을 판정기 입구에서 한 번**(`Core/PolicySanitizer.cs`). 이상하면 잠그지 않고 기록을 남긴다.
   `days` / `approvedOvertime`의 **null 원소**도 여기서 걸러낸다 — `PolicyModels.cs`의 `??=` 패턴은
   목록 자체만 막고 목록 안의 빈 칸은 막지 못한다(실측 확인).
   · 실제 구현은 `days` **1개 이상**이면 통과한다(2개 고정이 아니다). 1개만 와도 그날 판정은 가능하고,
     0개면 판정 불가로 떨어지므로 이쪽이 더 안전하다. 같은 날짜가 두 번 오면 앞의 것만 쓴다.
   · 유예 상한은 **서버(웹 설정 화면)와 같은 240분**으로 맞췄다. 앱 상한이 더 넓으면 서버가 막는 값이
     앱에서 통과해 "그 회사는 하루도 안 잠김"이 된다.
4. ✅ **테스트 모드는 실행 인자 `--test-mode`로만** (`Core/AppMode.cs`, 2-C에서 이행). 설정 파일(`config.json`)에 두면
   직원이 메모장으로 잠금을 영구 무력화할 수 있다(2-A 검수 치명 지적). 자동 시작 등록에는 이 인자를 넣지 않는다.

## 2-C에서 지킨 것 (2-B에서 남긴 약속) — ✅ 이행 확인

1. ✅ **`AppInfo.Version`을 `0.3.0`으로 올렸다** — 기록 전송과 **같은 커밋**에서.
   서버의 미보고 감시(`webapp/lib/pcoff-alert.ts`)가 **앱 버전 0.3.0 이상만 감시**하기 때문이다.
   기록 전송 없이 버전만 올리면 정상 PC가 전부 경고로 뜨고, 반대면 감시가 영원히 침묵한다.
   · `AppInfo.Version`과 `NewgaonPcOff.csproj`의 `<Version>` **둘 다** 올렸다(값이 어긋나면 안 된다).
2. ✅ **`PairWindow.xaml`의 `PendingNote` 줄을 지웠다** — 이제 실제로 잠기므로 그 문장은 거짓이 된다.
3. ✅ **일시사용 종료시각을 `LockDecider.Decide(..., tempUseUntil)`에 넘긴다**(`PolicyService.SafeDecide`).
4. ✅ **잠금·해제·사전알림·일시사용을 `/api/agent/events`로 보낸다**(오프라인 대기줄 포함).

## 2-C 설계 메모 (왜 이렇게 했는가)

| 결정 | 이유 |
|---|---|
| 기록은 **실제로 덮었을 때만** 남긴다(`LockController`) | 판정만 보고 남기면, 테스트 모드처럼 덮지 않은 순간까지 "잠갔다"고 보고하는 거짓말이 된다 |
| [일시사용] 종료시각은 **메모리에만** 둔다 | 파일에 두면 직원이 고쳐 잠금을 영구히 푸는 통로가 된다. 껐다 켜면 다시 잠기는 쪽이 안전하다(쓴 횟수는 서버가 세므로 되돌려지지 않는다) |
| 앱이 따로 세는 일시사용 횟수(`_tempUsedLocal`) | 서버의 `usedToday`는 기록이 서버에 닿아야 오른다. 그 사이에 다시 누르면 하루 1회 제한이 2회가 된다 |
| 기록이 생기면 **15초 뒤** 전송 | 평상시 확인 주기(5분)를 그대로 두면 방금 잠근 사실이 [PC관리]에 5분 뒤에야 뜬다 |
| 잠금 중에는 트레이 [종료]를 막는다 | 완전한 차단은 아니다(작업관리자로 끄면 꺼진다 — 그건 서버 감시가 잡는다). **메뉴 한 번으로 풀리는 것**만 막는다 |
| 사전알림은 여러 개가 걸려도 **하나만** 띄운다 | 앱을 6분 전에 켜면 10분·5분 알림이 동시에 걸린다. 알림 폭탄은 그 자체가 업무 방해다 |
| 잠금화면은 **알림창(MessageBox)을 띄우지 않는다** | 포커스를 되찾는 동작과 부딪혀 알림창을 누를 수 없게 된다. 안내는 전부 창 안의 글줄로 한다. 잠금 중에는 트레이 안내도 알림창 대신 **풍선**으로 나간다 |
| `PolicyService`에서 `ConfigureAwait(false)` **금지** | 실기기 검증에서 실제로 터진 버그 — 이후 처리가 화면 스레드 밖에서 돌아 트레이·잠금화면 갱신이 통째로 예외로 죽었다. `Recompute()`가 `Dispatcher.VerifyAccess()`로 이 전제를 못박는다 |
| 잠금화면은 **1초마다 스스로 점검**한다(최소화·숨김·최상위 해제를 되돌린다) | **Win+D(바탕화면 보기) 한 번으로 잠금이 완전히 풀리던 구멍**을 막는다. 최소화되면 `Activate()`로는 복원되지 않는다 |
| 못 보낸 [일시사용] 기록에서 **오늘 쓴 횟수를 이어받는다** | 없으면 랜선을 뽑고 앱을 껐다 켜는 것만으로 하루 허용 횟수를 무한히 넘길 수 있다 |

## 남은 위험 — 사장님 결정이 필요한 것 (2-A 검수 치명 C-3)

**설치형 앱의 구조적 한계**입니다. 지시서 §0이 워치독(강제종료 방지)을 범위 밖으로 둔 것과 같은 성질이라,
"클라이언트만으로는 못 막는다"는 점을 분명히 해 두고 **서버 쪽 보상 장치**로 메꾸는 것이 정석입니다.

| 구멍 | 지금 상태 | 막는 방법(결정 필요) |
