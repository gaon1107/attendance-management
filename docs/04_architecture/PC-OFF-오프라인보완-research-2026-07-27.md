# Research: PC-OFF 오프라인 보완 5건 (2026-07-27)

> 배경: 사장님 결정 — **PC-OFF는 회사 지급 PC 전용**이며, 회사 PC로 외근·재택을 나가는 상황을
> 정상 시나리오로 본다. 따라서 "인터넷이 없어도 통제는 이어지고, 직원이 갇히지는 않는다"를 목표로 한다.
> 시장조사 결론(같은 날): 업계는 오프라인 처리 사양을 공개하지 않으며, 넷클라이언트만
> "오프라인 관리정책 자동 전환"을 명시한다 → **표준이 없는 영역, 우리가 정한다.**

## 2. 🔴 영향 범위 — 수정 대상을 쓰는 모든 곳 (Grep 전수 확인)

### `buildPcOffPolicy` (lib/pcoff-policy.ts)
```
app/api/agent/policy/route.ts:16   ← 유일한 호출처
```
**결론: 호출처 1곳. 화면·다른 기능이 이 함수를 쓰지 않는다 → 파급 작음.**
단, 이 함수가 **읽는 데이터**(근무시각·근무요일·공휴일·연장근무 승인)는 다른 화면과 공유되므로
**읽기만 하고 절대 쓰지 않는다**는 현재 원칙을 유지해야 한다.

### `listPcOffUnreported` / `PCOFF_ALERT_GRACE_MIN` (lib/pcoff-alert.ts)
```
app/pc-devices/page.tsx:63,100     ← [PC관리] 화면
lib/notifications.ts:63            ← 관리자 알림센터 집계
```
**결론: 2곳. 이번 계획에서는 판정 로직을 바꾸지 않는다(화면 안내문만 추가) → 영향 없음.**

### 사건 종류 화이트리스트 (`ALLOWED_TYPES`)
```
app/api/agent/events/route.ts:11   ← 저장 시 거르는 곳
app/pc-devices/page.tsx:16         ← EVENT_LABEL(화면 라벨). 주석에 "짝이다(늘릴 때 함께)" 명시됨
lib/pcoff.ts:70                    ← SYSTEM_EVENT_TYPES(90일 보관 목록)
```
**결론: 종류를 하나 늘리면 위 3곳을 함께 봐야 한다. 주석이 이미 경고하고 있다.**

### 공통 모듈 판정
- `lib/pcoff.ts` = **공통 모듈**(서버·브라우저 양쪽에서 import). 상수를 추가만 하고 기존 값은 손대지 않는다 → safe-coding 절차상 "add-only"라 위험 낮음.
- `lib/pcoff-policy.ts` = PC-OFF 전용(호출처 1곳) → 공통 모듈 아님.
- `Core/LockDecider.cs` = 판정의 중심이지만 **이번에 수정하지 않는다.**

## 3. DB·API 변경 여부

| 항목 | 변경 | 비고 |
|---|---|---|
| **DB 스키마** | ❌ **없음** | 새 사건 종류는 기존 `AgentEvent.type`(문자열)에 값 하나 더 쓰는 것 → 마이그레이션 불필요 |

| **기록 API 요청** | 🟡 `type`에 `temp_use_offline` 값 추가 허용 | 옛 앱은 안 보내므로 무해 |
| **응답 크기** | +약 1.5KB (하루 50바이트 × 30일) | 5분 주기 폴링 기준 무시할 수준 |

## 4. 위험 요소

### 🔴 R1. "사흘째부터 안 잠기던" 구간이 사라진다 (의도된 변화, 그러나 체감 큼)
지금은 서버가 이틀치만 줘서 3일째부터 `NoDayInfo` → **안 잠금**(fail-open).
한 달치를 주면 **3일째부터도 잠긴다.** 목적상 맞지만, **현장 체감이 가장 큰 변화**다.
→ 계획서에서 사장님 확인 항목으로 명시한다.

### 🟡 R2. 정책 캐시에 담기는 값이 커진다
`PolicyCache`는 정책 JSON을 통째로 DPAPI 암호화해 저장한다. 1.5KB 증가 → 문제 없음.
**형식 번호(`CurrentVersion`)는 올리지 않아도 된다** — 배열 개수만 늘 뿐 구조가 같기 때문.
(올리면 기존 PC의 캐시가 버려져 **재연결 전까지 판정 불가 = 안 잠김** 구간이 생긴다 → 올리면 안 된다.)

### 🟡 R3. `PolicySanitizer.MaxDayDistance = 3`이 한 달치를 잘라낸다
현재 "서버 시각에서 3일 넘게 떨어진 날짜는 버린다". 이 값을 안 고치면 30일을 보내도 **3일치만 남는다.**
반드시 함께 수정해야 하는 짝이다.

### 🟡 R4. 오프라인 한도를 쓴 뒤 온라인으로 돌아오면 남은 횟수가 음수가 된다
`TempUseLeft = 한도 - 서버가센횟수 - 앱이센횟수`. 오프라인에서 6회 쓰고 복귀하면 한도(2회)보다 커진다.
현재 코드가 `Math.Max(0, ...)`로 감싸고 있어 **동작은 안전**하지만, 화면에 "0회 남음"만 뜬다.
→ 문구로 설명해야 한다("오프라인 중 사용분은 별도로 셉니다").

### 🟡 R5. 오프라인분을 하루 한도에서 빼지 않으면 "오프라인 위장" 우회가 생긴다
앱을 고쳐 항상 `temp_use_offline`으로 보내면 한도가 무의미해진다.
**단, 앱 변조 방어는 개발지시서 §0에서 범위 밖으로 정해져 있고**(작업관리자로 끄면 그만),
서버 미보고 감시가 유일한 방어선이라는 기존 결정과 일관된다. **기록이 남으므로 관리자가 본다.**
→ 새 위험이 아니라 **기존에 수용한 위험과 동급**. 계획서에 명시만 한다.

### 🟢 R6. 보관기간은 자동으로 안전한 쪽에 떨어진다 (확인 완료)
`pcoff-retention.ts:56`이 `type notIn 시스템목록` = 3년 보관으로 처리한다.
새 종류 `temp_use_offline`을 `SYSTEM_EVENT_TYPES`에 **넣지 않기만 하면** 자동으로 3년 보관(= 일시사용과 동일).
주석도 "새 종류를 넣는 걸 잊어도 근로기록이 일찍 지워지지 않는 쪽"이라 밝히고 있다.

### 🟢 R7. 공휴일 로딩은 범위 확대에 영향 없음 (확인 완료)
`loadOffDays`가 **연도 단위**로 읽는다(`yearsInRange`). 30일 범위가 연말을 넘어도 2개 연도를 읽을 뿐 정상.

### 🟢 R8. 판정기 성능 무영향 (확인 완료)
`LockDecider.FindChange`가 후보 시각을 모을 때 `Horizon = 48시간` 안쪽만 담는다(`Add()`의 `x <= limit`).
days가 30개여도 실제 후보는 지금과 같은 수준으로 유지된다.

## 5. 옛 버전 앱과의 호환 (중요)

| 상황 | 결과 |
|---|---|
| **0.3.0 앱 + 새 서버** | days 31개를 받지만 `MaxDayDistance=3`이 3일치만 남긴다 → **지금과 똑같이 동작**(더 나빠지지 않음) |
| **0.4.0 앱 + 옛 서버** | days 2개만 받는다 → 지금과 동일. 오프라인 긴급사용은 앱 단독 기능이라 그대로 작동 |
| 미보고 감시 | `supportsEventReports`는 `minor >= 3` 판정 → 0.4.0도 통과 ✅ |

**결론: 서버·앱 배포 순서를 신경 쓰지 않아도 된다.**

## 6. 결론 (계획 시 고려사항)

1. **DB 마이그레이션이 없다.** 되돌리기가 쉽다(git revert만으로 복구).
2. **호출처가 적다.** `buildPcOffPolicy` 1곳, 미보고 감시 2곳. 파급이 좁다.
3. **반드시 짝으로 고쳐야 하는 것 2쌍**
   - 서버 `days` 확대 ↔ 앱 `MaxDayDistance` (R3)
   - 새 사건 종류 ↔ 화이트리스트·화면 라벨·KPI 집계 (§2)
4. **캐시 형식 번호는 올리지 않는다** (R2).
5. **가장 큰 변화는 R1** — 오프라인 3일째부터 잠기기 시작. 사장님 확인 필요.
6. 미결정 1건: **오프라인 긴급사용 횟수 = 무제한 vs 하루 6회.**
