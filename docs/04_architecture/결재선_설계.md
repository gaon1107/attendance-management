# 결재선(다단계 승인) 설계·구현 계획서

> 작성: 2026-07-19 · 상태: **계획(승인 대기)** · 근거조사: [경쟁서비스 전체기능 조사](../01_market/03_경쟁서비스_전체기능_조사.md)
> 확정 결정(사장님): **부서장 자동 결재선** 방식 · 범위 = **부서장 자동 결재선(1~2단계) + 대결(대리결재) + 진행상태 표시** (전결·조건별·에스컬레이션은 2차)

---

## 1. 목표

회사마다 다른 결재 체계를, **관리자가 부서 조직도에 "부서장"을 지정하면 신청이 그 라인을 자동으로 타고 올라가** 승인되도록 한다. 국내 그룹웨어(네이버웍스·다우오피스·하이웍스)의 "자동 결재선"이 표준이며, 중소기업 사무직에 맞게 1~2단계로 최소화한다.

### 범위 (In)
- 부서에 **부서장** 지정 + **상위부서** 연결(부서 계층)
- 신청(휴가·근태정정) 시 **결재선 자동 생성**: 신청자 부서장 → 상위부서장 (회사가 정한 단계수)
- **결재함**: 부서장(직원 신분)도 자기 차례 신청을 승인/반려
- **진행상태 표시**: "2단계 중 1단계 승인, 2단계 대기"
- **대결(대리결재)**: 부서장 부재 시 대리인 지정 (없으면 관리자 폴백)
- **관리자 오버라이드**: 관리자는 언제든 전체 승인 가능(기존 권한 유지)

### 범위 (Out — 2차)
- 전결(중간에서 종결), 조건별 결재선("3일 이하는 팀장까지"), 자동 에스컬레이션(기한 초과 시 자동 넘김), 결재 의견 첨부 고도화, 근태정정 외 신규 신청유형

## 2. 핵심 설계 원칙 — "회귀 0"의 열쇠

### 원칙 A: 원본 신청의 `status`는 **전 과정 `pending` 유지**, 전원 승인 시에만 `approved`
- 조사 결과 **휴가 `status="approved"`를 읽는 소비처가 9곳**(dashboard·reports·records·my-records·records/[userId]·leave-summary·leave-summary/export·employees/[id]·lib/leave). 근태정정도 동일 패턴.
- 결재선 진행 중에는 원본이 계속 `pending`이므로 **이 9곳은 "아직 미승인"으로 보아 기존과 100% 동일하게 동작**한다. 마지막 단계 승인 순간에만 `approved`로 바뀐다.
- ⇒ 판정·집계 코드 **무수정**으로 회귀 0.

### 원칙 B: 결재선 미설정 회사는 **기존 단일 관리자 승인 그대로**
- 회사 설정 `approvalMode`: `single`(기본=기존) | `deptline`(결재선). 부서장 미지정이면 자동 `single` 취급.
- `single` 회사는 결재단계(ApprovalStep)를 만들지 않고 기존 `approveLeave/rejectLeave` 경로를 그대로 탄다.

### 원칙 C: 스키마는 **add-only**(nullable/기본값) — 기존 회사 데이터 무영향

## 3. 데이터 모델 변경 (add-only)

### 3-1. Department (부서) — 필드 추가
```
headUserId    String?   // 부서장(직원 1명). null이면 결재선에서 이 부서는 관리자 폴백.
parentId      String?   // 상위부서(부서 계층). null이면 최상위.
deputyUserId  String?   // 대결자(부서장 부재 시 대리결재). 선택.
```
- 자기참조(parentId)·User참조(head/deputy). 순환참조 방지 검증은 저장 액션에서.

### 3-2. Company — 필드 추가
```
approvalMode  String  @default("single")  // "single"(기존) | "deptline"(결재선)
approvalSteps Int     @default(1)          // 결재 단계 수(1~2 권장, 최대 3 방어)
```

### 3-3. 신규 모델 `ApprovalStep` (결재 단계 — 진행상태 기록)
```
id            String   @id @default(cuid())
companyId     String                       // 회사격리
requestType   String                       // "leave" | "correction"
requestId     String                       // LeaveRequest.id 또는 AttendanceCorrection.id
stepOrder     Int                          // 1,2,3...
approverUserId String                      // 이 단계 결재자
status        String   @default("pending") // pending | approved | rejected
decidedAt     DateTime?
comment       String?                      // 반려/승인 사유(선택)
createdAt     DateTime @default(now())
@@index([companyId, requestType, requestId])
@@index([approverUserId, status])          // 결재함 조회
```
- 원본(LeaveRequest/AttendanceCorrection)은 스키마 **무변경** — 다형 참조(requestType+requestId)로 연결.

## 4. 순수 로직 (lib) — 테스트 가능하게 분리

`lib/approval.ts` (순수함수, 임시라우트로 테스트):
- `buildApprovalChain(applicant, deptMap, steps)` → 결재자 userId 배열
  - 신청자 부서의 headUserId부터 시작 → parentId 타고 상위부서 head → steps개 수집
  - **자기 자신은 건너뜀**(부서장이 신청하면 그 단계 skip)
  - head 없으면 대결(deputy) → 없으면 관리자 폴백 표시
  - 중복 결재자 제거, 순환참조 방어(최대 깊이 제한)
- `nextPendingStep(steps)` → 다음 처리할 단계
- `isChainComplete(steps)` / `isChainRejected(steps)` → 원본 status 전환 판정

## 5. 서버 액션 변경 (영향 범위)

| 파일 | 변경 | 회귀 위험 |
|---|---|---|
| `actions/leave.ts` `requestLeave` | `deptline`이면 결재선 계산 후 ApprovalStep 생성(트랜잭션). `single`이면 기존 그대로 | 낮음(분기 추가) |
| `actions/leave.ts` `approveLeave`/`rejectLeave` | 결재자 권한 = "현재 단계 approverUserId==me" 또는 admin. 단계 승인→다음, 마지막→원본 approved. 반려→원본 rejected | **중** — 권한 로직 변경, 정밀 검증 필요 |
| `actions/corrections.ts` | 위와 동일 패턴. 단 근태정정 승인은 실제 기록 반영 로직 포함(101줄) → **최종 단계 승인 시에만** 반영 | **중** |
| `actions/departments.ts`(부서관리) | 부서장·상위부서·대결자 저장 + 순환참조 검증 | 낮음(신규 필드) |
| `settings`(회사설정) | approvalMode·approvalSteps 저장 | 낮음 |

**권한 모델 변경(핵심)**: 현재 승인은 `role==="admin"` 전용. 결재선 모드에선 **부서장(직원 신분)도 자기 차례를 승인**해야 하므로, 승인 액션에 "현재 단계 결재자면 허용" 분기를 추가한다. 관리자는 기존처럼 전체 가능.

## 7. 단계별 구현 계획 (Phase)

각 Phase 종료 = tsc·eslint 0 + 순수함수/실DB 임시라우트 검증 + code-reviewer + git 커밋.

- **Phase 1 — 토대(스키마+순수로직, 화면 미연결)**: schema 3종 변경 + 마이그레이션 + `lib/approval.ts` 순수함수 + 경계테스트. **회귀 0**(add-only, 미사용).
- **Phase 2 — 설정 UI**: 부서관리(부서장·상위부서·대결자) + 회사설정(approvalMode·steps) 저장. 순환참조 방어.
- **Phase 3 — 결재선 생성·진행(핵심)**: 신청 시 ApprovalStep 생성 + 결재함(`/approvals`) + 승인/반려 단계진행 액션 + 최종단계서 원본 status 전환. `single` 회사는 기존 경로 유지 검증.
- **Phase 4 — 진행상태·알림**: 신청 상세 진행상태 표시 + 종배지/알림센터/사이드바 [결재함] 연동.
- **Phase 5(선택) — 대결·다듬기**: 부서장 부재표시→대결 자동전환, 관리자 폴백 UX, 반려사유 입력.

## 8. 검증 계획
- **순수함수**: `buildApprovalChain`(부서장 신청=자기건너뜀·상위없음·순환·중복·폴백 등) 경계 임시라우트.
- **실DB 통합**: 검증DB(뉴가온)에 2계층 부서+부서장 심어 신청→단계승인→최종 approved 확인 후 **원상복구**(실계정 무오염).
- **회귀 0 확인**: `single` 회사(하늘테크)에서 휴가 승인/판정이 기존과 동일한지 E2E.
- **실화면 E2E**: 부서장 직원 로그인→결재함→승인, 진행상태·알림 확인.
- **code-reviewer**: Phase 3·4 필수(권한 로직 변경 지점 집중 검수).

## 9. 위험 요소 / 알려진 한계
- **권한 로직 변경**(승인=단계결재자 허용)이 가장 예민 — 회사격리·타인 결재건 차단 정밀 검증 필요.
- **근태정정 최종 반영 시점**: 여러 단계여도 실제 기록 반영은 **마지막 승인 1회만**(중복반영 금지).
- **부서 계층 순환참조**(A→B→A) 저장 시 차단 필수(무한루프 방지).
- **부서장 신분 = employee**: 결재함 접근을 role이 아닌 "결재자 여부"로 게이트 → 기존 admin 전용 화면들과 혼동 없게 분리.
- 한계(수용): 조건별 결재선·전결·자동 에스컬레이션 없음(2차). 반차/시간단위 등 신청유형 확장과는 독립.
