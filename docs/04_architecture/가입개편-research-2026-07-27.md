# Research: 회사 가입 개편 + 회사 계정·관리자 지정 (2026-07-27)

> 목적: 사장님 지적 2건 — ①"관리자가 퇴사하면 회사가 잠긴다" ②"가입 정보가 너무 적고 인증이 없다" 의 실제 코드 상태와 영향 범위를 확인한다.

---

## 1. 지금 가입은 이렇게 동작한다

**화면** `webapp/app/signup/page.tsx` — 입력 4개: 회사명 · 이름(관리자) · 이메일 · 비밀번호
**서버** `webapp/app/actions/auth.ts:12~53` `signup()`

```
Company 생성 → User 생성(role="admin") → 세션 발급 → /onboarding
```

- 이메일 **중복만** 검사. 실재 여부·인증 **없음**.
- 사업자등록번호·전화·약관동의 **받지 않음**.
- `role: "admin"`을 쓰는 곳은 **이 한 줄뿐**(전수 검색 확인) → 관리자를 만드는 유일한 경로가 "회사 가입".

## 2. 관리자 자리 문제 (사장님 지적 ①) — 사실 확인

| 확인 항목 | 결과 | 근거 |
|---|---|---|
| 관리자 추가 지정 | **불가** | 직원 등록·초대가 전부 `role:"employee"` 고정 (`employees.ts:41`, `invites.ts:80`) |
| 관리자 퇴사 처리 | **불가** | `employees.ts:131` — `target.role === "admin"`이면 즉시 return |
| 대표 계정 이관 | **없음** | 해당 기능 자체가 없음 |
| 관리자 비번 분실 복구 | **없음** | 직원 비번은 관리자가 발급(`resetEmployeePassword`), 관리자 본인은 발급해 줄 사람이 없음 |

→ **결론: 관리자 1명이 나가거나 비번을 잊으면 그 회사 데이터에 아무도 접근할 수 없다.** 제품 결함이 맞다.

## 3. 🔴 가장 중요한 발견 — 관리자는 근태 집계에서 빠진다

`role: "employee"`로 거르는 곳이 **9군데** 있다(전수 검색):

| 파일 | 무엇이 빠지나 |
|---|---|
| `app/dashboard/page.tsx:36` | 대시보드 오늘 출근 현황 |
| `app/employees/page.tsx:24` | **직원 목록에 관리자가 아예 안 보임** |
| `app/leave-summary/page.tsx:37`, `export/route.ts:29` | 연차 현황·엑셀 |
| `app/shifts/page.tsx:49,83`, `actions/shift.ts:96` | 교대 스케줄 배정 대상 |
| `actions/employees.ts:41`, `actions/invites.ts:80` | (생성 시 역할 고정 — 집계 아님) |

지금은 관리자가 1명뿐이라 티가 안 났지만, **관리자를 여러 명 만들면 그 사람들이 통째로 근태 집계에서 사라진다.** 중소기업에서 총무 담당(=관리자)도 출퇴근을 찍으므로 실무상 치명적이다.

→ 이번 작업의 진짜 위험은 "권한"이 아니라 **이 9군데의 필터**다.

## 4. 권한 검사 117군데 — 건드리지 않아도 되는 이유

`role !== "admin"` / `role === "admin"` 검사가 **66개 파일 · 117군데**에 있다.
회사 계정을 새 역할(`role="owner"`)로 만들면 이 117군데를 전부 고쳐야 하고, 하나라도 빠지면 회사 계정이 그 화면에서 튕긴다.

→ **회사 계정도 `role="admin"`으로 두고, 표시 하나(`isOwner`)만 더한다.** 117군데는 손대지 않는다(저장소 관례인 add-only).

## 5. 인증 수단 — 지금 실제로 가능한 것

| 수단 | 상태 | 근거 |
|---|---|---|
| **사업자등록번호 진위확인** | ✅ **지금 가능** | 공공데이터포털 무료 API. `.env`에 `HOLIDAY_API_KEY`가 이미 있어 **같은 포털 계정을 쓰고 있음** → 신규 API 신청만 하면 됨(1~2시간) |
| **이메일 인증** | ❌ **수단 없음** | 메일 발송 라이브러리·서비스가 저장소에 전혀 없음(nodemailer·resend·SMTP 전무). 새로 계약·연동 필요 |
| **휴대폰 문자 인증** | ⚠️ **코드는 있으나 미작동** | `lib/sms.ts`(아이원24) 존재. 그러나 `.env`에 `IONE_SMS_ID/PW/SENDER` **없음** → 계정 키 확보 전엔 발송 불가 |
| PASS 본인인증 | ❌ | 별도 계약·건당 과금. 근태 SaaS 업계 표준 아님 |

## 6. 약관 동의 — 아예 없다

- `app/page.tsx:209`에 "이용약관 · 개인정보처리방침" **글자만** 있고 링크·문서·동의 체크박스가 없다.
- 개인정보보호법상 수집·이용 동의는 **필수**. 특히 우리는 얼굴(민감정보)을 다루므로 더 엄격하다.
- 문서(약관 본문) 작성 자체가 별도 과제 → 법무 영역.

## 7. 경쟁사(시프티) 실제 가입 화면 — 2026-07-27 직접 확인

- 입력: 이메일 · 비밀번호 · 이름 · 전화번호(선택) · 시간대 + 약관 동의 3개. 구글·네이버 로그인 지원.
- **사업자등록번호 안 받음. 휴대폰 본인인증 없음.**
- 회사는 가입 후 "회사 만들기"로 생성. **최고관리자가 회사를 만들고, 아니면 "권한 이임"으로 넘김.**
- 출처: https://shiftee.io/ko/accounts/register , https://shiftee.io/ko/help/article/createCompany

→ 업계 원칙은 **"가입은 쉽게, 검증은 돈 낼 때"**. 우리도 무료체험 단계에서 서류를 요구하면 이탈한다.

## 결론 (계획 시 고려사항)

1. `role`을 새로 만들지 말고 `isOwner` 표시 하나만 추가 → 117군데 무영향.
2. **9군데의 `role:"employee"` 필터 교체가 이번 작업의 핵심 위험**. 여기서 회귀가 나면 근태 숫자가 틀어진다.
3. 이 교체의 부수 효과: **박성헌(관리자)이 대시보드·연차현황에 새로 나타난다.** 옳은 동작이지만 기존 화면이 달라지므로 사장님께 알려야 한다.
4. 인증은 **사업자등록번호만 1차에 넣는다.** 이메일·문자는 발송 수단이 확보되지 않아 지금 만들면 "동작하지 않는 기능"이 된다.
5. 약관 **동의 기능**은 만들되, **약관 본문**은 법무 과제로 분리한다.
