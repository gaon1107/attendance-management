# GPS·위치 인증 설계서 (gps-spec)

> **담당**: GPS·위치 인증 전용 에이전트 (gps-verify)
> **작성일**: 2026-07-04
> **입력 근거**: [requirements.md](../02_prd/requirements.md), [screen-inventory.md](../03_design/screen-inventory.md), [wireframes.md](../03_design/wireframes.md), [face-spec.md](face-spec.md), [CLAUDE.md](../../CLAUDE.md) 법적 가드레일
> **확정 전제**: 위치 판정은 **우리 백엔드**에서 처리(A안, 관리형 백엔드/DB). 회사가 온보딩에서 사업장 위치·허용 반경 등록(회사 초기설정 화면 3-1). 얼굴인증 거부 직원도 **GPS만으로 정상 출퇴근 가능**(강제 금지).

---

## 0. 이 문서를 한 장으로 요약하면 (비개발자용)

- GPS는 **얼굴인증을 원치 않는 직원의 핵심 대체 수단**이다. 그래서 GPS만으로도 출퇴근이 100% 정상 처리되어야 한다.
- 출퇴근 버튼을 누르면 브라우저가 **현재 위치(위도·경도)를 한 번** 측정하고, 우리 서버가 **"회사가 등록한 사업장 반경 안인가?"**만 판정한다. 반경 안이면 출퇴근 시각을 기록한다.
- 우리는 **판정에 필요한 최소 정보만** 저장한다. **이동경로(동선)는 저장하지 않고, 평소에 위치를 계속 추적하지도 않는다.** 위치는 **출퇴근 버튼을 누른 그 순간에만** 딱 한 번 확인한다.
- GPS는 실내·건물 밀집 지역에서 **오차가 크다.** 이럴 때를 위해 WiFi/IP 보조 확인을 **정책 옵션**으로 제시한다.
- ⚠️ **솔직한 한계**: 우리는 **모바일 웹(브라우저)** 환경이다. 앱(네이티브)과 달리 **가짜 위치앱(Mock Location) 사용 여부를 브라우저가 직접 알려주지 않는다.** 그래서 위조를 100% 막을 수는 없고, "탐지 가능한 신호로 의심스러운 경우를 걸러내는" 수준까지가 현실적 한계다. 남는 위험은 [8]에서 보안·법무 검토로 넘긴다.

## 1. 위치 인증 흐름 — 출퇴근 시 한 번만 위치 확인

```
[직원 브라우저]                 [우리 백엔드]                    [우리 DB]
출퇴근 버튼 클릭
  → 브라우저 위치 API 호출
    (Geolocation, 1회)
  → {위도, 경도, accuracy}  ──▶  위치 판정 로직
    + (보조) WiFi/IP 신호        - 사업장 목록 조회
                                 - 지오펜스(반경) 이내 판정 ──▶  판정결과·시각·사업장만 저장
                                 - 위조 신호 점검              (이동경로 저장 안 함)
  결과(반경 이내/밖) ◀──────────  출퇴근 기록 or 예외 안내
```

**원칙**
- 위치는 **출퇴근 버튼을 누른 순간에만 1회** 측정한다. 백그라운드 추적·주기적 측정을 **하지 않는다.** (상시 위치추적 금지 — 법적 가드레일)
- **판정은 우리 백엔드에서** 한다. 브라우저가 보내온 좌표를 그대로 믿고 화면에서 "합격"을 그리지 않는다. (좌표 조작 대비 — [4])
- 위치정보의 **원본 좌표는 판정에만 쓰고, 저장은 최소화**한다([6]).

### 1-1. GPS 단독 흐름 (얼굴인증 미선택 직원 — 핵심 대체 수단)

| 순서 | 동작 | 화면 |
|---|---|---|
| 1 | 직원이 메인 화면에서 [출근하기]/[퇴근하기] 클릭 | 1-4 메인/출퇴근 |
| 2 | 브라우저가 위치 권한 확인 → 현재 위치 1회 측정 | 1-7 GPS 확인(위치 확인 중) |
| 3 | 백엔드: 사업장 반경 이내 판정 + 위조 신호 점검 | (서버) |
| 4 | 반경 이내 → 출퇴근 시각 기록(F-08 3년 보존 연결) / 반경 밖 → 안내 | 1-7 성공/실패 분기 |

### 1-2. 얼굴 + GPS 동시확인 흐름 (얼굴인증 선택 직원 — 보조 수단)

> face-spec [7-2]가 라이브니스(위조 방지) 보완책으로 **"GPS + 얼굴 동시확인"**을 채택했다. 이 문서가 그 GPS 쪽을 담당한다.

**순서(권장): 얼굴 인식을 먼저, 위치는 같은 출퇴근 동작 안에서 함께 확인**

| 순서 | 동작 | 판정 |
|---|---|---|
| 1 | [출근하기] 클릭 → 얼굴인증 촬영(1-6) + 동시에 위치 1회 측정 | — |
| 2 | 얼굴: face-spec [2-1] 규칙(본인·유사도) 통과 | 얼굴 OK |
| 3 | GPS: 사업장 반경 이내 판정 | 위치 OK |
| 4 | **얼굴 OK 그리고(AND) 위치 OK** → 출퇴근 기록 | 둘 다 통과 시 기록 |
| 5 | 얼굴 실패 → face-spec [8] 폴백(재촬영 → GPS 대체) / 위치 실패 → [7] 예외 처리 | 분기 |

- **조합 규칙**: 얼굴 선택 직원은 **얼굴 AND 위치** 둘 다 만족해야 정상 기록(원격 대리 인증 차단 목적, face-spec [7-1] #4).
- **단, 얼굴이 계속 실패**하면 face-spec 폴백에 따라 **GPS 단독(1-1)으로 전환**할 수 있다. 이때는 GPS만으로 출퇴근이 완료된다(얼굴 강제 금지 원칙 유지).
- **위치 실패 시(반경 밖 등)**: 재시도 후에도 실패하면 [7] 예외 처리(관리자 수동 보정 여지 포함). 얼굴이 통과했더라도 사업장 밖이면 정상 출근으로 자동 기록하지 않는다(원격 대리 방지).

## 2. 허용 반경(지오펜스) 설정 — 회사가 온보딩에서 등록

### 2-1. 등록 방식 (회사 초기설정 화면 3-1 연계)

- 관리자가 **회사 초기설정 온보딩 2단계**에서 사업장을 등록한다(wireframes 3-1).
  - 주소 검색 → 지도에서 위치 확인 → **중심 좌표(위도·경도)** 확정
  - **허용 반경(m)** 입력 (예: 기본값 100m)
- 지오펜스 = **중심 좌표를 기준으로 반경 N미터의 원**. 출퇴근 시 측정한 위치가 이 원 안이면 "사업장 내"로 본다.

### 2-2. 반경 설정값 가이드

| 사업장 유형 | 권장 반경 | 이유 |
|---|---|---|
| 단독 건물/작은 사무실 | 50~100m | GPS 기본 오차(수십 m)를 감안한 최소 여유 |
| 대형 건물·오피스텔 밀집 | 100~200m | 건물 밀집 지역은 GPS 오차가 커서 여유 필요 |
| 넓은 부지(공장·캠퍼스) | 부지 크기에 맞춤(관리자 조정) | 물리적 부지가 넓으면 반경도 넓혀야 함 |

- 반경은 **관리자가 언제든 조정 가능**하게 둔다(근무제·기준시간 설정 화면).
- ⚠️ **트레이드오프(쉬운 말)**: 반경을 **좁히면** 부정(근처에서 찍고 안 옴)은 줄지만 **정상 직원이 반경 밖으로 튕겨** 출근 실패가 늘어난다. 반경을 **넓히면** 정상 직원은 편하지만 **건물 밖·주차장·옆 건물에서도 출근 처리**될 수 있다. → 회사 환경에 맞게 관리자가 조절. 기본값은 여유 있게(100m) 시작 권장.

### 2-3. 다중 사업장 지원 (F-15는 P2 — 1차는 "구조만" 열어둠)

- requirements.md에서 **다중 사업장(F-15)은 P2**다. 따라서 **1차 MVP는 "한 회사 = 사업장 여러 개 등록 가능"한 데이터 구조만 준비**하고, 사업장 전환 UI 등 고급 기능은 만들지 않는다(과설계 방지).
- 판정 로직은 처음부터 **"등록된 여러 사업장 중 하나라도 반경 이내면 통과"**로 설계한다(사업장 목록을 순회). 이렇게 하면 나중에 F-15를 켤 때 판정 로직을 다시 안 짜도 된다.
- 1차에서 회사가 사업장을 1개만 등록하면 그 1개로만 판정한다(동일 로직, 목록 길이 1).

> **경계**: 사업장별 근무시간 차등, 직원-사업장 배정, 사업장 전환 화면 등은 **F-15(P2)** 영역이라 이 문서에서 만들지 않는다. "여러 개 등록·다중 판정"까지만 1차 범위.

## 3. 정확도·실내 오차 대응 — WiFi/IP 보조 확인

### 3-1. 문제: GPS는 실내·건물 밀집 지역에서 오차가 크다

- 브라우저 위치 API는 좌표와 함께 **정확도(accuracy, 단위 m)**를 준다. 이 값이 클수록 "이 좌표는 대략 이 반경 안 어딘가"라는 뜻으로 부정확하다.
- 실내·지하·고층빌딩 밀집 지역에서는 accuracy가 수백 m까지 나빠질 수 있다. 이때 좌표만으로 반경 판정을 하면 **정상 직원이 자꾸 반경 밖으로 튕기는** 문제가 생긴다.

### 3-2. 정확도(accuracy) 임계값 처리

| accuracy 상태 | 처리 |
|---|---|
| accuracy가 충분히 정확(예: 반경 대비 여유 있음) | GPS 좌표로 바로 반경 판정 |
| accuracy가 나쁨(설정 임계값 초과, 예: 200m 이상) | GPS만으로 판정 보류 → **보조 확인(WiFi/IP)** 시도 → 그래도 애매하면 재측정 안내 → 반복 실패 시 [7] 예외 |
| 위치를 아예 못 받음(신호 없음/타임아웃) | 재시도 안내 → 계속 실패 시 [7] 폴백(관리자 보정 여지) |

> accuracy 임계값의 **구체 수치**는 회사 환경에 따라 달라서 **파일럿 실측으로 확정**한다(사무실이 실내 깊은 곳이면 완화 필요). 우선 "반경 + accuracy 여유"를 함께 보는 방식으로 시작한다.

### 3-3. 보조 확인 정책 (WiFi/IP) — 정책 옵션으로 제시

> **선택지를 제시하고, 최종 채택은 보안·법무 검토([8]) + 사장님 결정으로 확정한다.** 아래는 강도 순 정책안이다.

| 정책안 | 판정 규칙 | 장점 | 단점/한계 |
|---|---|---|---|
| **A. GPS 단독(엄격)** | GPS 반경 이내만 인정 | 단순·명확 | 실내 오차 시 정상 직원 실패 잦음 |
| **B. GPS 또는 WiFi/IP(관대, 권장)** | **GPS 반경 이내 "또는" 회사 WiFi/IP 확인 중 하나라도 통과 시 인정** | 실내 오차 보완, 정상 직원 편의 | 부정 가능성 약간 증가(회사 WiFi 근처에서 우회) |
| **C. GPS 그리고 보조(엄격+보조)** | GPS가 애매할 때만 보조를 **가산 조건**으로 사용 | 균형 | 로직 복잡, 실패 케이스 여전 |

- **1차 권장: 정책 B(하나라도 통과 시 인정)** — GPS의 실내 한계를 실무적으로 보완하고, "얼굴 거부 직원도 무리 없이 GPS 출퇴근"이라는 핵심 목표에 부합한다.
- **WiFi 보조의 현실**: 모바일 웹(브라우저)은 **연결된 WiFi의 이름(SSID)이나 주변 AP 목록을 직접 읽지 못한다**(브라우저 보안 정책). 그래서 실무적으로 쓸 수 있는 보조 신호는 주로 **① 브라우저 Geolocation이 내부적으로 WiFi를 활용해 계산한 좌표** ② **회사 네트워크의 공인 IP 대역**이다.
  - **IP 대역 확인**: 회사가 고정 공인 IP(사무실 인터넷)를 쓰면, 출퇴근 요청이 그 IP 대역에서 왔는지 백엔드가 확인할 수 있다. "사무실 WiFi에 붙어 있음"의 간접 증거로 활용.
  - ⚠️ **한계**: 공인 IP는 회사가 고정 IP를 계약해야 유효하고, VPN·모바일 데이터(LTE/5G)로 접속하면 회사 IP가 아니게 된다. 그래서 **IP는 보조(보완) 신호로만** 쓰고 단독 인증 근거로 삼지 않는다.

> **채택 시 회사 설정 필요값**: 정책 B/C를 켜려면 회사가 **자사 공인 IP 대역**을 등록해야 한다(근무제·기준시간 설정에 추가). 고정 IP가 없는 회사는 정책 A(GPS 단독) 또는 반경 완화로 운영.

## 4. 위조 방지 — 가짜 위치앱·VPN·좌표 조작 (모바일 웹 한계 솔직히 명시)

> **대전제(솔직한 고백)**: 우리는 **모바일 웹(브라우저)**이다. 네이티브 앱과 달리 브라우저는 "지금 가짜 위치앱(Mock Location)이 켜져 있는지"를 **표준적으로 알려주지 않는다.** 따라서 아래 방어는 **"완전 차단"이 아니라 "의심 신호 탐지·마찰 부여"** 수준이다. 완전 차단이 필요하면 [8]에서 네이티브 앱/전문 솔루션 도입을 검토한다.

### 4-1. 위협별 대응과 한계

| 위협 | 무엇인가 | 우리가 할 수 있는 것 | 한계(솔직히) |
|---|---|---|---|
| **가짜 위치앱 (Mock Location)** | 폰의 GPS 좌표를 소프트웨어로 조작 | ① 좌표가 사업장 정중앙에 **너무 정확히** 찍히거나 accuracy가 비현실적으로 완벽한 패턴 탐지 ② 짧은 시간 좌표가 **물리적으로 불가능하게 점프**하면 의심 처리 ③ **얼굴+GPS 동시확인**으로 원격 조작 부담 상승 | 브라우저에서 Mock 여부 **직접 확인 불가**. 정교한 조작은 통과 가능 → [8] 이관 |
| **VPN / 프록시** | 접속 IP를 다른 지역으로 위장 | ① 요청 IP의 지역과 GPS 좌표 지역이 **크게 어긋나면** 의심 플래그 ② 알려진 VPN/데이터센터 IP 대역이면 보조 IP 확인을 **신뢰하지 않음** | VPN 자체를 막지는 않음(정상 사용자도 씀). GPS가 조작 안 됐으면 VPN만으로 위치를 속이진 못함(위치는 GPS 기반). **IP 보조 정책을 쓸 때만** 영향 |
| **좌표 조작 (요청 위변조)** | 브라우저가 보내는 좌표 JSON을 중간에서 바꿔치기 | ① **판정은 100% 백엔드에서** ② 출퇴근 요청에 **서버 발급 1회용 난수(nonce)+짧은 유효시간** 부여(사전 준비/재사용 차단, face-spec [7-1] #2와 동일 메커니즘 공유) ③ 요청은 **HTTPS 전용**(중간 변조 차단) ④ **기기(deviceId) 바인딩**(face-spec [7-1] #3 공유) | 루팅/개발자도구로 자기 브라우저에서 좌표를 넣는 것은 완전 차단 불가 → 의심 신호로 관리 |

### 4-2. 위조 의심 시 처리 (차단이 아니라 "플래그 + 마찰")

- 위조 **의심 신호가 잡히면** 자동으로 정상 기록하지 않고 **"의심 플래그"**를 남긴다 → 관리자에게 노출(대시보드 "주의 필요 직원") → **관리자 확인/보정**([7]).
- 무고한 직원(실내 오차·VPN 정상 사용)이 억울하게 막히지 않도록, **즉시 거부보다 재시도·보조확인·관리자 검토** 경로를 우선한다.
- **얼굴+GPS 동시확인**(1-2)은 그 자체로 강력한 위조 억제책이다(원격에서 남의 위치+얼굴을 동시에 위조하기 어려움).

### 4-3. 남는 위험 (→ [8] 보안·법무 검토로 이관)

- 모바일 웹에서는 **Mock Location 정밀 탐지, 루팅 탐지, 앱 무결성 검증**이 근본적으로 불가능하다.
- **완전한 위치 위조 방지가 사업상 꼭 필요하면**, 네이티브 앱(Mock 탐지 API 사용) 또는 전문 위치 무결성 솔루션 도입이 필요하다. 이 **도입 여부·비용·잔여 위험 수용**은 이 문서 범위를 넘어 **security-architect([08_security])가 판단**한다.

## 5. 프라이버시 (법적 가드레일 — 절대 규칙)

> CLAUDE.md: **위치정보 최소수집 · 상시 위치추적 금지 · 대체수단 보장.** 아래는 이를 설계로 못박은 것.

### 5-1. 4대 원칙

1. **최소 수집**: 출퇴근 판정에 필요한 순간에만, 필요한 최소 정보만 수집한다.
2. **상시 추적 금지**: 백그라운드·주기적 위치 수집을 하지 않는다. **출퇴근 버튼을 누른 그 순간 1회만** 측정.
3. **이동경로 미저장**: 동선(어디를 거쳐 왔는지)을 **저장하지 않는다.** 우리는 "출근 시각에 사업장 안이었다/밖이었다"만 안다.
4. **목적 제한**: 위치정보는 **출퇴근 판정 목적으로만** 쓴다. 마케팅·감시 등 다른 목적으로 쓰지 않는다.

### 5-2. 수집 항목·보관기간·동의 (GPS 사용 동의 화면 1-5 연계)

| 구분 | 내용 |
|---|---|
| **수집 항목** | 출퇴근 시점의 위도·경도, 정확도(accuracy), (정책 B/C 사용 시) 접속 IP. **판정에 쓰는 최소 항목만.** |
| **수집 시점** | 직원이 **출퇴근 버튼을 누른 순간에만.** 그 외 시간에는 수집하지 않음. |
| **이용 목적** | 회사가 등록한 **사업장 반경 이내 여부 확인**(출퇴근 기록). 그 외 목적 사용 안 함. |
| **보관 대상·기간** | **판정 결과(사업장 내/외)·출퇴근 시각·사업장 식별자**는 근로기록으로 **3년 보존**(F-08, 근로기준법). **원본 좌표는 보관하지 않거나 최소화**([6]). |
| **동의 범위** | GPS 사용 동의 화면(1-5)에서 "위치는 사업장 반경 확인용으로만, 이동경로는 추적 안 함"을 고지하고 위치 권한 허용을 받는다. |
| **거부권·불이익 없음** | 위치 권한을 거부하면 [7] 대체 경로(관리자 보정 등)로 안내. 위치정보 제공 거부로 근무 기록을 못 남기는 상황을 만들지 않는다. |

> GPS 사용 동의 화면(wireframes 1-5)에 이미 **"회사가 등록한 사업장 반경 이내인지만 확인하며, 이동경로는 별도로 추적하지 않습니다"** 문구가 반영되어 있다. 본 설계는 그 문구와 정합한다.

## 6. 우리 측 데이터 — 무엇을 저장하고, 무엇을 저장하지 않는가

### 6-1. 우리 DB에 저장하는 것 (판정 결과·최소값)

| 저장 항목 | 예시 | 이유 |
|---|---|---|
| 출퇴근 판정 결과 | `insideGeofence: true/false` | 사업장 내/외 여부(근로기록) |
| 출퇴근 시각 | `checkedAt` | 법정 기록(F-08, 3년 보존) |
| 매칭된 사업장 식별자 | `siteId` | 어느 사업장에서 찍었는지 |
| 인증 수단 | `method: gps / face+gps` | 어떤 방식으로 인증했는지 |
| (선택) 위조 의심 플래그 | `suspicious: true`, 사유 코드 | 관리자 검토용([4-2]) |
| GPS 사용 동의 상태/일시 | `gpsConsented`, `consentedAt` | 동의 증빙 |

### 6-2. 우리 DB에 **저장하지 않는(또는 최소화하는) 것**

- ❌ **이동경로/동선** — 출퇴근 순간 외의 위치를 저장하지 않는다.
- ❌ **상시 위치 로그** — 백그라운드 위치를 남기지 않는다.
- ⚠️ **원본 좌표(위도·경도)** — 판정에만 쓰고, **저장하지 않는 것을 기본**으로 한다. (분쟁·감사 목적으로 최소 보관이 필요하다는 판단이 서면 **보관 여부·기간을 [8] 보안검토에서 확정**한다. 이 문서는 "기본 미저장, 필요 시 최소·기간한정"을 권고선으로 제시.)
- ❌ **정밀 accuracy 원본의 장기 보관** — 판정 후 결과값(내/외)만 남기고 원본 수치는 남기지 않음(권고).

> 이렇게 하면 우리 시스템은 **"직원이 언제 어디에 있었는지"를 축적하지 않는 구조**가 된다. 위치정보 유출 위험과 "상시 감시" 논란을 구조적으로 줄인다(생체정보를 GaonFR로 위임해 원본을 안 갖는 face-spec [3]과 같은 철학).

## 7. 예외 / 폴백 처리 (얼굴 강제 금지 + 근무기록 누락 방지)

| 상황 | 우리 처리 | 화면 |
|---|---|---|
| **위치 권한 거부** | "위치 없이는 GPS 출퇴근 확인이 어렵습니다" 안내 → 권한 재요청 안내 → 그래도 거부 시 **관리자 수동 보정** 경로 안내(근무기록 자체는 남길 수 있게) | 1-5 / 1-7 |
| **반경 밖** | "사업장 반경 밖입니다. 위치를 다시 확인해주세요" → 재시도. 반복 실패 & 실내 오차 의심 시 보조확인([3]) → 그래도 안 되면 관리자 보정 | 1-7 반경 밖 |
| **신호 없음/타임아웃** | 재측정 안내(수 초 대기) → 계속 실패 시 보조확인 또는 관리자 보정 경로 | 1-7 |
| **accuracy 나쁨(실내 오차)** | GPS 판정 보류 → 보조확인([3-3]) → 애매하면 재시도/보정 | 1-7 |
| **위조 의심** | 자동 통과 막고 **의심 플래그** → 관리자 대시보드 "주의 필요 직원"에 노출 → 관리자 확인·보정([4-2]) | 3-2 대시보드 |
| **얼굴 실패(얼굴 선택자)** | face-spec [8] 폴백 → **GPS 단독(1-1)으로 전환**해 출퇴근 완료 가능 | 1-6 실패 → 1-7 |

### 7-1. 관리자 수동 보정 (핵심 안전장치)

- 위 예외로 자동 기록이 안 된 경우, **관리자가 근태 현황에서 해당 출퇴근을 수동으로 인정/보정**할 수 있다(직원이 실제 출근했는데 GPS 오차로 실패한 케이스 구제).
- 수동 보정은 **누가·언제·왜 보정했는지 로그**를 남긴다(감사·법정 증빙). 남용 방지를 위해 관리자 권한으로만.

> **핵심 원칙**: 어떤 예외 상황에서도 **직원이 근무 기록을 남기지 못하는 상태로 방치하지 않는다.** GPS가 실패해도 관리자 보정으로 구제 가능. 얼굴이 실패해도 GPS로 전환 가능. (얼굴 강제 금지 + 근로기록 누락 방지 동시 충족)

## 8. 다른 단계로 넘기는 결정 사항 (경계 명시)

- **보조확인 정책 최종 채택(A/B/C)** + **IP 보조 사용 여부**: → 사장님 결정 + security-architect 검토.
- **원본 좌표 보관 여부·기간**: → **[8] 보안·법무 검토(security-architect)**가 최종 판단([6-2]).
- **위치 위조 잔여 위험 수용 / 네이티브 앱·전문 솔루션 도입 여부**: → security-architect([4-3]).
- **accuracy 임계값·반경 기본값의 실측 확정**: → **파일럿**에서 회사 환경별로 측정해 확정([2-2],[3-2]).
- **위치 판정 API 명세·DB 스키마(저장 필드 확정)**: → **시스템 설계 단계**(docs/04_architecture).
- **GPS 동의 화면 문구·시각 디자인 상세**: → UX/UI 상세 단계(문구 골격은 wireframes 1-5에 반영됨).
- 본 문서는 **위치 인증 흐름·지오펜스·보조확인 정책·위조 방지 범위·프라이버시 경계·예외 폴백**까지만 책임진다. (요청 범위 밖 기능 추가 안 함)
