# 얼굴인증 연동 설계서 (face-spec)

> **담당**: 얼굴인증·실근무시간 전용 에이전트 (face-auth)
> **작성일**: 2026-07-04
> **입력 근거**: [requirements.md](../02_prd/requirements.md), [screen-inventory.md](../03_design/screen-inventory.md), [CLAUDE.md](../../CLAUDE.md) 법적 가드레일
> **연동 대상(확정)**: 사내 얼굴서버 **GaonFR** (`https://gaonfr.newgaon.com`) API 연동
> **참조한 실제 연동 코드**: newgaon-LMS `faceEnrollService.js`(등록/삭제), 공식 샘플 `sample02.js`(토큰/recognize/detect/enrollment/unenrollment/all), `mobile_attendance.js`(모바일 출결 흐름), `consent-face-recognition.html`(생체정보 동의서 선례)

---

## 0. 이 문서를 한 장으로 요약하면 (비개발자용)

- 우리 앱은 얼굴을 **직접 알아보지 않는다.** 카메라로 찍은 사진을 **사내 얼굴서버(GaonFR)**에 보내서 "이 사람 맞아?"를 물어보고, **답(맞다/아니다)만** 받는다.
- 그래서 우리 데이터베이스에는 **얼굴 사진도, 얼굴 특징값도 저장하지 않는다.** 우리는 "이 직원은 GaonFR에 어떤 번호(FaceId)로 등록돼 있다"는 **연결 정보만** 갖는다. 실제 얼굴은 GaonFR가 보관한다.
- 얼굴인증은 **강제하지 않는다.** 원치 않는 직원은 GPS로 출퇴근한다. GaonFR가 고장 나도 GPS로 출퇴근할 수 있게 한다.
- ⚠️ **주의**: GaonFR는 "지금 진짜 사람이 앞에 있는지"(라이브니스/위조 방지)를 **판별하지 못한다.** 그래서 사진·영상으로 남 대신 찍는 부정을 막는 보완책을 **우리 앱에서** 만들어야 한다. 이 문서 [7]에서 다루되, 남는 위험은 [5단계] 보안·법무 검토로 넘긴다.

## 1. 연동 아키텍처 — "GaonFR 어댑터" 한 곳에서만 호출

```
[직원 브라우저]                [우리 백엔드]                     [사내 얼굴서버]
카메라 촬영  ──이미지──▶  얼굴인증 API   ──▶  ┌──────────────────┐  ──▶  GaonFR
(실시간)                 (우리 서버)         │ GaonFR 어댑터     │       (얼굴 보관·판정)
                                            │ (연동 계층)       │
결과(성공/실패) ◀────────  출퇴근 기록 저장 ◀│ - 토큰 캐시·재발급 │  ◀──  판정결과
                          (우리 DB)         │ - 4016/401/403/   │       (PascalCase)
                                            │   429 시 1회 재시도│
                                            │ - HTTPS 전용      │
                                            └──────────────────┘
```

**원칙**
- GaonFR로 나가는 **모든 호출은 "GaonFR 어댑터"라는 단 하나의 연동 모듈**을 통해서만 나간다. 다른 코드가 GaonFR를 직접 부르지 않는다. (교체·장애대응·로그를 한 곳에 모으기 위함)
- 어댑터는 다음 4가지 공통 처리를 책임진다:
  1. **토큰 관리**: 앱 토큰(`ApiToken`)을 메모리에 캐시하고, 만료 시 자동 재발급.
  2. **재시도**: 토큰만료(`StatusCode 4016`)·`401`·`403`·`429` 응답 시 → 토큰 재발급 후 **1회만** 재시도. (LMS `faceEnrollService.js`, 샘플 `wrapAjax`와 동일 규칙)
  3. **비밀값 격리**: `ClientToken` 등 비밀값은 어댑터가 **환경변수(env)**에서만 읽는다. 소스·문서·로그에 남기지 않는다.
  4. **응답 정규화**: GaonFR 응답은 PascalCase(`StatusCode`, `Faces[]`, `FaceId`, `Similarity` 등) → 우리 앱 내부에서 쓰기 쉬운 형태로 변환.
- **이미지는 통과만 시킨다(pass-through).** 어댑터는 촬영 이미지를 GaonFR로 전달만 하고, **디스크·DB에 저장하지 않는다.** 전송 후 메모리에서 폐기.

### 1-1. 인증(토큰) 흐름 — 실제 규격

| 순서 | 요청 | 헤더 | 응답 |
|---|---|---|---|
| 1 | `POST /get/token/` | 요청 헤더 `ClientToken: <env 비밀값>` | **응답 헤더** `ApiToken` 로 앱 토큰 수신 (본문 아님) |
| 2 | 이후 모든 API 호출 | 요청 헤더 `ApiToken: <위에서 받은 값>` | 각 API 결과 |
| 3 | 토큰 만료/인증 실패 시 (`4016`/`401`/`403`/`429`) | — | 1로 돌아가 재발급 → 원래 요청 **1회** 재시도 |

> ⚠️ 앱 토큰은 응답 **본문이 아니라 헤더(`ApiToken`)**로 내려온다. (샘플 `getResponseHeader('ApiToken')`, LMS `res.headers.get('ApiToken')` 확인)

### 1-2. GaonFR 엔드포인트 요약 (확인된 규격)

| 용도 | 메서드/경로 | 본문 형식 | 주요 필드 |
|---|---|---|---|
| 토큰 발급 | `POST /get/token/` | (헤더 `ClientToken`) | 응답 헤더 `ApiToken` |
| 얼굴 등록 | `POST /v1/face/enrollment/` | multipart | `Image`, `FaceId`, `Group` |
| 본인 인식(출퇴근) | `POST /v1/face/recognize/` | multipart | `Image`, `Group` → 응답 `Faces[].FaceId`, `Faces[].Similarity` |
| 얼굴 검출(자리 유무) | `POST /v1/face/detect/` | multipart | `Image` → 응답 `Faces[]`(개수만 사용) |
| 등록 삭제(파기) | `POST /v1/face/unenrollment/` | x-www-form-urlencoded | `FaceId[]`, `Group` |
| 등록 목록 | `POST /v1/face/all/` | form | `Group` → 응답 `Faces[]` |

> **개발/운영 서버 분리**: 개발 단계는 `https://gaonfrdev.newgaon.com`, 운영 배포 전 우리 웹 도메인을 가온 측에 통보 후 `https://gaonfr.newgaon.com` 사용. 두 값 모두 `FACE_API_BASE_URL`(env)로만 관리한다. (샘플 상단 주석 근거)

### 1-3. 식별자 매핑 (절대 임의 변경 금지)

| GaonFR 필드 | 우리 시스템 값 | 설명 |
|---|---|---|
| `FaceId` | **직원 ID(문자열)** | 우리 DB의 직원 고유 id. 등록·인식·삭제에서 **글자 단위로 동일**해야 같은 얼굴로 취급됨 |
| `Group` | **회사(테넌트) 식별자** | 회사별로 얼굴 등록 영역을 분리. 다른 회사 직원과 섞이지 않게 하는 칸막이 |

> LMS 선례: `FaceId=학생 id`, `Group=학원 로그인 아이디`. 우리는 `FaceId=직원 id`, `Group=회사 식별자`로 대응. 인식 결과 `FaceId`가 `'Unknown'`이면 미등록/타인으로 처리(샘플 `faceId !== 'Unknown'` 판정 근거).

## 2. 기능 매핑 — 우리 요구사항 ↔ GaonFR API

| 우리 기능(F-ID) | 화면 | 쓰는 GaonFR API | 우리가 하는 일 |
|---|---|---|---|
| **F-03 얼굴 등록(선택)** | 생체정보 동의 → 얼굴 등록 | `enrollment` | 동의 확인 후 촬영 이미지+`FaceId`(직원id)+`Group`(회사) 전송. 성공 시 우리 DB에 "등록됨" 표시 |
| **F-05 얼굴인증 출퇴근** | 얼굴인증 촬영(출퇴근) | `recognize` | 촬영 이미지+`Group` 전송 → `Faces[0].FaceId`가 **본인 id와 일치 + `Similarity` 임계값 이상**이면 출퇴근 기록 |
| **F-06 실근무시간(옵션 B)** | 근무 중 자리확인 안내(옵션 B) | `detect` | 근무 중 주기적으로 촬영 → **얼굴 개수(있음/없음)만** 받아 자리 유무 기록. **이미지·누구인지 저장 안 함** |
| **F-10 파기(퇴사·철회)** | 내 정보/얼굴 삭제, 관리자 동의·파기 관리 | `unenrollment` | `FaceId[]`+`Group` 전송으로 GaonFR에서 삭제 + 우리 참조데이터 삭제 + 파기 이력 로그 |
| (운영 점검용) 등록 현황 대조 | 관리자 동의·파기 관리 | `all` | 회사(`Group`) 등록 목록을 받아 우리 DB "등록됨" 상태와 대조(불일치 점검) |

> **F-09 동의**는 API 호출이 아니라 **F-03 등록 직전의 필수 전제**다. 동의 없이는 `enrollment`를 호출하지 않는다([6] 참조).

### 2-1. F-05 인식 판정 규칙 (본인 확인)

1. `recognize` 응답 `Faces` 배열을 확인한다.
2. 얼굴이 **정확히 1개**이고, 그 `FaceId`가 **로그인한 본인의 직원 id와 일치**하며, `Similarity`가 **회사 설정 임계값 이상**일 때만 → **통과**.
3. 얼굴이 0개/2개 이상, `FaceId`가 `'Unknown'`이거나 타인 id, 유사도 미달 → **실패**.
4. 실패 시 재시도 안내(다시 촬영) + 연속 실패 한도 초과 시 GPS 대체수단 안내([7] 라이브니스·[7-2] 폴백).

> 여러 얼굴이 잡히면(뒤에 다른 사람) 대리·오인 위험이 있으므로 **1명일 때만 통과**시킨다. (샘플도 `faces.length === 1`일 때만 성공 처리)

## 3. 우리 측 데이터 — 무엇을 저장하고, 무엇을 저장하지 않는가

### 3-1. 우리 DB에 저장하는 것 (참조값·상태값만)

| 저장 항목 | 예시 | 이유 |
|---|---|---|
| 직원 ↔ FaceId 매핑 | `employeeId → FaceId(=직원id 문자열)` | 인식·삭제 시 어떤 직원인지 연결 |
| Group(회사 식별자) | 회사 id | 회사별 칸막이 |
| 얼굴등록 여부 | `enrolled: true/false` | 등록 완료 상태 표시 |
| 생체정보 동의 상태/일시 | `consented: true`, `consentedAt`, `consentVersion` | 법적 동의 증빙 |
| 파기(철회) 이력 | `unenrolledAt`, 사유, 처리자 | 파기 증빙 로그 |
| 옵션 B 자리 기록 | 시각 + **`present: 있음/없음`** | 실근무시간 산출용 (이미지 아님) |

### 3-2. 우리 DB에 **절대 저장하지 않는 것**

- ❌ **얼굴 이미지(사진)** — 전송만 하고 저장 안 함. GaonFR가 보관. **단 하나의 예외 = 아래 "출퇴근 촬영 사진"**.
- ❌ **얼굴 특징값/템플릿(벡터)** — 우리는 만들지도, 받지도, 저장하지도 않는다. GaonFR 내부에만 존재.
- ❌ **옵션 B의 촬영 이미지** — `detect`로 "얼굴 개수"만 받고, **이미지는 저장하지 않는다.** 결과도 "있음/없음"만 기록(누구 얼굴인지 식별하지 않음).

#### ⚠️ 유일한 예외 — 출퇴근 촬영 사진 (사장님 확정 2026-07-11, 구현 완료)

- **무엇**: 얼굴 출퇴근에 사용된 촬영 사진 **전건**을 위조 판독(라이브니스) 점수와 함께 보관한다. 관리자가 근태 이력에서 "본인 확인 재검토"용으로만 열람.
- **차단 없음**: 판독 점수가 낮아도 출퇴근은 정상 처리(조용한 표시). 직원 화면에는 아무 표시 없음.
- **보호 장치**: AES-256-GCM 암호화 · 웹 공개경로 밖(webapp/storage/) 저장 · 관리자만 열람 + 열람 기록(누가·언제) · **90일 자동 파기**(파일만 삭제, 점수 기록은 보존) · 키는 .env(CLOCK_PHOTO_KEY).
- **동의**: 생체정보 동의 화면(consent)에 "출퇴근 촬영 사진 90일 보관 후 자동 삭제" 항목 포함(2026-07-11 반영). 문구 변경 시 보관기간 상수(lib/clock-photo.ts)와 일치 유지.
- 관련 구현: `webapp/lib/liveness.ts`(판독) · `webapp/lib/clock-photo.ts`(암호화·파기) · `ClockPhoto` 테이블 · `/api/clock-photo/[id]`(열람).

> 이렇게 하면 우리 시스템은 **생체정보 원본을 보관하지 않는 구조**가 되어 보관 부담·유출 위험을 GaonFR로 위임한다. GaonFR가 개인정보 처리 **수탁자**가 되며, 위탁 사실을 동의서에 명시한다([6], LMS 동의서 "4. 처리의 위탁" 선례).

> ⚠️ **옵션 B의 법적 성격은 [5단계] 보안·법무 검토에서 재확인 필요**: "이미지 미저장·검출여부만 기록"이 생체정보 규제를 실제로 완화하는지는 requirements.md §3에 명시된 대로 security-architect가 최종 판단한다.

## 4. 플로우 상세 (등록 / 인증 / 자리확인 / 파기)

### 4-1. 얼굴 등록 플로우 (F-03, F-09)

```
직원: 인증방식 선택("얼굴인증 사용하기")
  → 생체정보 동의 화면 (목적·항목·보관·파기·위탁·거부권 고지)
  → [동의] 체크 없으면 여기서 중단 (등록 불가)
  → 얼굴 등록 화면: 실시간 카메라 촬영 (업로드 불가)
  → 어댑터: POST /v1/face/enrollment/ (Image, FaceId=직원id, Group=회사)
  → 성공(Faces 1개 이상, StatusCode<4000): 우리 DB에 enrolled=true, consentedAt 기록
  → 실패: 서버 메시지 안내 후 재촬영 / GPS로 전환 안내
```

### 4-2. 출퇴근 인식 플로우 (F-05)

```
직원: 메인 출퇴근 화면에서 [출근] 또는 [퇴근]
  → 얼굴인증 촬영 화면: 실시간 카메라만 (사진 업로드 차단)
  → 서버가 발급한 1회용 난수(nonce)+유효시간 확인 (재사용·사전촬영 방지, [7])
  → 어댑터: POST /v1/face/recognize/ (Image, Group)
  → 판정([2-1] 규칙): Faces 1개 + FaceId==본인 + Similarity>=임계값 → 통과
  → 통과: 출퇴근 시각 기록 (F-08 법정 기록 3년 보존과 연결)
  → 실패: 재촬영 안내 → 연속 N회 실패 시 GPS 대체 출퇴근 안내
```

### 4-3. 근무 중 자리확인 플로우 (F-06, 옵션 B)

```
사전 고지: "몇 분마다 자리확인용으로 카메라가 짧게 작동합니다" 배너 (동의·투명성)
  → 설정된 주기(예: 10~15분)마다 짧게 촬영
  → 어댑터: POST /v1/face/detect/ (Image)  ※ recognize 아님 = 누구인지 식별 안 함
  → 응답 Faces 개수>=1 → present=있음, 0 → present=없음
  → 우리 DB: 시각 + 있음/없음만 기록 (이미지·신원 저장 안 함)
  → 실근무시간 = 근무시간 - (연속 '없음' 구간 합)  ※ 구체 산식은 시스템 설계 단계에서 확정
```

> **프라이버시 경계(옵션 B)**: ① 상시 촬영 금지(짧은 주기 샘플링만) ② 이미지 미저장 ③ `detect`만 사용(신원 식별 안 함) ④ 사전 고지·동의 범위 안에서만 작동 ⑤ 직원이 얼굴인증을 선택하지 않으면 옵션 B도 동작하지 않음.

### 4-4. 파기 플로우 (F-10)

```
계기: 직원 동의 철회 / 직원 얼굴 삭제 / 퇴사 처리
  → 어댑터: POST /v1/face/unenrollment/ (FaceId[]=직원id, Group=회사)
  → 성공: 우리 DB의 매핑·enrolled 삭제, unenrolledAt·사유·처리자 로그 기록
  → 실패: 재시도 큐에 넣고 관리자 알림 (미파기 상태가 남지 않도록 추적)
  → 파기 이력은 감사(audit) 목적으로 별도 보존 (얼굴 자체가 아니라 "언제 파기했다"는 로그)
```

## 6. 동의 · 파기 연결 (법적 가드레일)

### 6-1. 동의 (F-09) — 등록 전 필수

- **얼굴 등록 전, 생체정보 별도 동의**를 받는다. 동의 없으면 `enrollment` 호출 자체를 하지 않는다.
- 동의서에 담을 항목 (LMS `consent-face-recognition.html` 선례를 근태용으로 각색):
  1. **수집 항목**: 얼굴 이미지 및 얼굴 특징점(본인 확인·출퇴근 처리용). ※ 항목은 GaonFR가 보관하고 우리는 참조값만 보유함을 명시.
  2. **이용 목적**: 얼굴인증을 통한 **본인 확인 및 출퇴근 기록**, (옵션 B 사용 시) 근무 중 자리 유무 확인.
  3. **보유·이용 기간**: 재직 기간 또는 **동의 철회 시까지**. 목적 달성·철회 시 **지체 없이 파기**.
  4. **처리 위탁**: 얼굴인식 처리 업무를 **뉴가온(GaonFR)**에 위탁함을 고지.
  5. **거부권·불이익 없음**: 동의를 거부할 수 있으며, 거부 시 **GPS 대체수단**으로 출퇴근한다. **거부해도 근무·인사상 불이익 없음**(얼굴인증 강제 금지 원칙).

### 6-2. 파기 (F-10)

- 철회·퇴사 시 `unenrollment`로 **GaonFR에서 실제 파기** + 우리 참조데이터 삭제 + **파기 이력 로그**.
- 파기 실패 시 재시도·관리자 알림으로 "미파기 잔존"을 방지([4-4]).
- 관리자 화면(생체정보 동의·파기 관리)에서 동의 현황·파기 이력을 조회·증빙.

## 7. ⚠️ 라이브니스(위조 방지) — GaonFR 미지원에 대한 앱 레벨 보완책

**문제**: GaonFR는 라이브니스(살아있는 실제 사람인지) 판별을 **지원하지 않는다.** 따라서 **타인의 사진·동영상·마스크로 대리 인증**을 GaonFR 단독으로는 막을 수 없다. 위조 방지는 **우리 앱에서** 보완해야 하며, 이는 정확도보다 우선한다.

### 7-1. 보완책 후보 비교

| # | 방안 | 막는 위협 | 위조 방지 효과 | 구현 부담 | MVP 채택 |
|---|---|---|---|---|---|
| 1 | **실시간 카메라 촬영만 허용, 파일 업로드 차단** | 저장된 사진·영상 파일 제출 | 중 | 낮음 | ✅ 필수 |
| 2 | **서버 발급 1회용 난수(nonce)+짧은 유효시간** | 미리 찍어둔 이미지 재사용·리플레이 | 중~상 | 낮음 | ✅ 필수 |
| 3 | **촬영 시각·기기(deviceId) 바인딩** | 다른 기기·다른 시간대 촬영 우회 | 중 | 낮음 | ✅ 필수 |
| 4 | **GPS + 얼굴 동시 확인** | 사업장 밖 원격 대리 인증 | 중 | 낮음(GPS 재사용) | ✅ 권장 |
| 5 | **연속 실패 횟수 제한 + 잠금/관리자 알림** | 반복 시도(사진 각도 바꿔 뚫기) | 중 | 낮음 | ✅ 필수 |
| 6 | **무작위 동작 요구**(눈깜빡임·고개돌리기) | 정지 사진(1장) 위조 | 상 | **높음** (연속 프레임·동작 판정 로직 필요) | ⏳ 2차 검토 |
| 7 | 전문 라이브니스 엔진 도입(별도 벤더) | 사진·영상·마스크 전반 | 최상 | 매우 높음(비용·연동) | ⏳ 보안검토 후 결정 |

### 7-2. 1차 권장안 (MVP)

**"실시간 촬영 전용(1) + 1회용 nonce·유효시간(2) + 시각·기기 바인딩(3) + GPS 동시확인(4) + 연속 실패 제한(5)"의 조합**을 1차 기본값으로 채택한다.

- 이 조합은 **구현 부담이 낮으면서** "저장된 사진 파일 업로드", "미리 찍어둔 이미지 재사용", "원격 대리" 같은 **가장 흔한 부정**을 상당 부분 차단한다.
- 폴백 규칙: 얼굴인증 연속 실패(예: N회) 또는 GaonFR 장애 시 → **GPS 대체 출퇴근**으로 전환 안내(얼굴 강제 금지 원칙 유지, [8]).

### 7-3. 남는 위험 (→ [5단계] 보안·법무 검토로 이관)

- 위 조합으로도 **정교한 위조(고화질 동영상 재생, 정밀 3D 마스크, 화면-대-화면 촬영)**는 완전히 막지 못한다.
- 이 **잔여 위험의 수용 여부, 무작위 동작 요구(6)·전문 라이브니스 엔진(7) 도입 여부, 위조 시 법적 책임 분담**은 이 문서 범위를 넘는다. → **security-architect(보안·법무 검토, [08_security])에서 최종 판단**한다. 본 설계서는 "GaonFR가 라이브니스를 지원하지 않는다"는 사실과 앱 레벨 보완책·잔여 위험을 **명시적으로 넘긴다.**

## 8. 에러 / 장애 처리 (얼굴 강제 금지 원칙 유지)

| 상황 | GaonFR 신호 | 우리 처리 |
|---|---|---|
| 앱 토큰 만료 | `StatusCode 4016` / `401` / `403` | 토큰 재발급 후 **1회 재시도** (어댑터가 자동) |
| 요청 과다 | `429` | 잠시 후 재시도(반복 재발급 금지). 인식 반복 루프에서만 다음 프레임으로 넘어감(샘플과 동일) |
| 인식 실패(본인 아님/미검출) | `Faces` 0개·`Unknown`·유사도 미달 | 재촬영 안내 → 연속 N회 실패 시 **GPS 대체 안내** |
| GaonFR 서버 장애/응답 없음 | HTTP 5xx·타임아웃 | 사용자에게 "얼굴서버 일시 오류" 안내 + **즉시 GPS 대체 출퇴근으로 폴백** |
| 등록 실패 | `StatusCode>=4000` | 서버 메시지 표시 후 재시도, 계속 실패 시 GPS만 사용 안내 |
| 파기 실패 | `StatusCode>=4000` | 재시도 큐 + 관리자 알림(미파기 잔존 방지) |

> **핵심**: 어떤 오류·장애에서도 **얼굴인증을 강제하지 않는다.** 항상 GPS 대체수단(F-04)으로 출퇴근할 수 있게 하여 직원이 근무 기록을 남기지 못하는 상황을 막는다.

## 9. 검증 기준 (완료 조건) — 이 설계가 만족해야 할 것

| 기준 | 본 문서의 정의 |
|---|---|
| 본인 인식 정확도 목표·측정 | 판정 규칙([2-1])에 `Similarity` 임계값 기반 통과. **구체 목표수치(예: 오인식률/미인식률)와 임계값은 파일럿 실측으로 확정** — GaonFR가 반환하는 `Similarity` 분포를 회사 환경에서 측정해 설정. (임계값은 회사 설정으로 조정 가능하게 둠) |
| 오인식(타인 통과) 허용 범위 | 보안상 **오인식은 미인식보다 위험** → 임계값을 보수적으로(높게) 시작. 타인 통과 의심 시 로그로 추적. 최종 허용치는 보안검토에서 확정 |
| 미인식(본인 거부) 허용 범위 | 본인 거부 시 재촬영 → 연속 실패 시 GPS 폴백으로 **업무 차질 없음** 보장. 허용치는 파일럿 측정 후 조정 |
| 라이브니스 우회 대응 | 사진/동영상/3D마스크 시나리오를 [7]에서 다룸. MVP 조합 제시 + 잔여 위험 보안검토 이관 |
| 생체정보 처리의 보안검토 통과 형태 | 원본 미저장([3]), 별도 동의·위탁 고지([6]), 파기·이력([4-4],[6-2]), 비밀값 env([5]), HTTPS·이미지 미보관([5]) — security-architect가 검토 가능한 형태로 정리 |
