## 0. 한 장 요약 (사장님용)

**결론부터: 이 서비스의 가장 중요한 방어선인 "회사 간 칸막이"는 뚫리지 않았습니다.**

사장님이 1순위로 꼽으신 "다른 회사 데이터 접근"을 가장 집중해서 팠습니다. 서버액션 32개, API 17개,
화면 53개를 전부 확인했고 **취약점 0건**입니다. 남의 회사 직원 정보·근태·얼굴사진·문서를 URL이나
요청값을 바꿔 가져오는 공격은 **한 곳도 성립하지 않습니다.** 개인정보 대량 유출 위험은 현재 낮습니다.

**대신 다른 종류의 위험이 나왔습니다 — "데이터를 훔치는" 공격이 아니라 "서비스를 멈추는" 공격입니다.**

가장 심각한 것은 **로그인 창구 하나로 서버 전체를 멈출 수 있다**는 것입니다(Critical 1건).
비밀번호를 맞힐 필요도, 계정을 알 필요도 없습니다. 그냥 로그인 요청을 계속 보내기만 하면 됩니다.
서버가 멈추면 **전 회원사 직원이 출퇴근을 찍지 못합니다.**

특이한 점은, **이 위험을 이 코드가 이미 알고 있었다**는 것입니다. 운영자(본사) 로그인 문에는
똑같은 위협을 막는 장치가 들어 있는데(1분 30건 상한), 정작 가장 많이 노출된 **고객사 로그인에는
그 장치가 빠져 있습니다.** 그래서 이건 "몰라서 못 막은 것"이 아니라 "한 곳에 안 붙인 것"이고,
고치는 것도 이미 있는 코드를 옮겨 붙이는 수준입니다.

그 다음은 **외부 라이브러리(남이 만든 부품)의 알려진 취약점**입니다. 우리가 쓰는 Next.js 버전에
공개된 HIGH 등급 결함이 9건 있고, 얼굴 사진을 처리하는 `sharp`에도 4건이 있습니다. 우리 코드가
잘못된 게 아니라 **부품을 최신으로 갈아야 하는 문제**입니다.

#### 문제 설명 (쉬운 말)

비밀번호를 확인하는 계산(`scrypt`)은 일부러 **느리게** 만들어져 있습니다. 공격자가 비밀번호를
빠르게 대입하지 못하게 하려는 정상적인 설계입니다. 1회에 약 40밀리초가 걸립니다.

문제는 이 계산이 **"동기(synchronous)" 방식**이라는 것입니다. 쉽게 말해 **계산하는 40밀리초 동안
서버가 다른 일을 하나도 못 합니다.** 그 순간 출퇴근을 찍는 직원, 화면을 여는 관리자 모두 멈춰 서서
기다립니다.

그리고 **없는 이메일로 로그인해도 이 계산이 똑같이 돌아갑니다.** 이건 의도된 것으로,
"응답이 빠르면 없는 계정"이라는 것을 공격자가 눈치채지 못하게 하려는 방어입니다. 방어 자체는 옳습니다.

```ts
// app/actions/auth.ts:236-238
const passwordOk = user
  ? verifyPassword(password, user.passwordHash)
  : (verifyPassword(password, DUMMY_HASH), false);   // ← 없는 계정도 40ms 소모
```

현재 꺼져 있습니다**(`TRUST_PROXY` 미설정 — 이건 의도된 안전 기본값입니다). IP를 모르면 제한은
그냥 통과시킵니다.

#### 수정 방법 (구체적)

**이미 있는 코드를 옮겨 붙이면 됩니다. 새로 만들 것이 없습니다.**

1. `lib/operator-policy.ts`의 `operatorDoorAllows()`와 **같은 구조**의 전역 상한 함수를 만든다
   (또는 그 파일에 고객사용 상한을 추가한다).
2. `app/actions/auth.ts`의 `login()`에서 **`verifyPassword`를 부르기 전에** 그 상한을 확인하고,
   넘었으면 **비밀번호 대조 없이** 기존과 똑같은 문구(`"이메일 또는 비밀번호가 올바르지 않습니다."`)로 거부한다.
   - ⚠️ 반드시 대조 **전에** 막아야 한다. 대조 후에 막으면 CPU는 이미 소모된 뒤라 아무 의미가 없다.
3. 상한값은 운영자문(1분 30건)보다 넉넉해야 한다. 고객사 로그인은 정상 트래픽이 있다.

4. 같은 처리를 `password-reset.ts`의 두 창구에도 적용한다.

⚠️ **이 수정은 사규상 "무거움" 등급입니다** — 로그인은 공용 경로이고, 상한을 잘못 잡으면

`lib/session.ts:15-21`의 주석이 스스로 이렇게 적고 있습니다: **"로그인을 못 하면 복구 수단이 0"**.

#### 공격 가능 시나리오

공격자가 대상의 이메일 하나만 알면 됩니다(가입 화면으로 이메일 존재 여부를 확인할 수 있습니다 — 5-M2).
10분마다 틀린 비밀번호 5개를 보내는 것만으로 그 계정을 **영구히 잠급니다.**
회사 계정을 표적으로 삼으면 **그 회사의 마스터 열쇠가 상시 잠긴 상태**가 되고,
서버에 직접 들어가 DB를 고치는 것 외에 복구 방법이 없습니다.

#### 예상 피해

- 관리자 계정 잠금 → 승인·급여 업무 중단
- 회사 계정 잠금 → **해당 회사 영구 잠김**(고객 이탈 직결)

#### 수정 방법

1. **연속 재잠금에 지수적 대기 적용** — 1회 10분, 2회 30분, 3회 2시간… 이렇게 늘리면 공격 효율이 급감합니다.
2. **회사 계정(`isOwner`)은 잠금 대신 지연(delay)만 적용** — 이 계정은 잠기면 복구가 없으므로,
   "막는 것"보다 "느리게 하는 것"이 안전합니다.
3. **근본 해결: 회사 계정 복구 경로를 만든다** — `lib/owner-recovery.ts`가 이미 준비되어 있고
   스위치만 꺼져 있습니다. 이걸 켜는 것이 정공법입니다(별도 계획 필요).

### H-3. 얼굴 사진을 처리하는 `sharp`에 알려진 취약점 4건

| 항목 | 내용 |
|---|---|
| **위험도** | **High** |
| **파일** | `webapp/package.json` — `"sharp": "^0.34.5"` (설치본 0.34.5), 사용처 `webapp/lib/liveness.ts:80,93`, `webapp/lib/quality.ts:17,29` |
| **기능** | 얼굴 출퇴근 — 라이브니스(사진 위조 판독) · 이미지 품질 검사 |
| **우선순위** | **운영 전 수정 권장** |

#### 문제 설명

`sharp`는 이미지 처리 라이브러리이고, 내부적으로 `libvips`라는 C 라이브러리를 씁니다.
그 `libvips`에 공개된 결함 4건이 있습니다(CVE-2026-33327, 33328, 35590, 35591).

**왜 중요한가**: 이 라이브러리가 처리하는 것이 **직원 브라우저에서 보낸 얼굴 사진 바이트**입니다.
즉 **공격자가 내용을 마음대로 정할 수 있는 데이터**가 취약한 네이티브 코드에 직접 들어갑니다.

```ts
// lib/liveness.ts:80  — imageBuffer는 클라이언트가 보낸 사진
const meta = await sharp(imageBuffer).metadata();
```

이미지 라이브러리의 메모리 관련 결함은 최악의 경우 **서버에서 임의 코드 실행(서버 침투)**까지
이어질 수 있는 유형입니다. 다만 실제 악용 난이도는 CVE마다 다르고, 여기서는 실증하지 않았습니다.

#### 공격 가능 시나리오 (안전 범위 설명)

1. 공격자가 회원가입 → 얼굴 출퇴근 기능 사용 설정
2. 정상 사진 대신 **특수하게 조작된 이미지 파일**을 출퇴근 촬영 데이터로 전송
3. 서버의 `sharp`가 그 파일을 해석하다 결함을 건드림
4. 결함 종류에 따라 서버 프로세스 중단(서비스 마비) 또는 그 이상

#### 수정 방법

```bash
cd webapp ; npm install sharp@^0.35.4
```

- ⚠️ `sharp` 0.34 → 0.35는 **breaking change**입니다. 업그레이드 후 반드시
  **얼굴 출퇴근 전 과정(등록 → 촬영 → 라이브니스 판정 → 사진 저장)을 실제로 돌려 확인**해야 합니다.
- 함께 나온 `onnxruntime-node` → `adm-zip`(조작된 ZIP으로 4GB 메모리 할당) 취약점은,
  ZIP을 읽는 대상이 **우리가 함께 배포하는 모델 파일**이라 외부 입력이 아닙니다. 실질 위험은 낮습니다.

### H-4. `TRUST_PROXY` 미설정 상태 — IP 기반 방어 6종이 전부 "켜진 척"만 하고 있음

| 항목 | 내용 |
|---|---|
| **위험도** | **High** |
| **파일** | `webapp/lib/ip.ts:13-26`, `webapp/lib/login-throttle.ts:73,116,153`, `webapp/lib/ip-block.ts:24,35`, `webapp/lib/agent-auth.ts:52` |
| **기능** | 접속 IP 기반 방어 전반 |
| **우선순위** | **배포 시 조치(코드 수정 아님) + 화면 표시 개선은 다음 업데이트** |

#### 문제 설명

접속자 IP를 믿지 않는 것은 **의도된 안전 기본값**이며 그 판단 자체는 옳습니다
(2026-08-02 검수 H-1의 결과물). 문제는 **그 결과로 무엇이 꺼졌는지가 화면에 드러나지 않는다**는 것입니다.

| 기능 | 코드 위치 | IP를 모를 때 실제 동작 |
|---|---|---|
| 로그인 IP 시도 제한 | `login-throttle.ts:116` | 항상 통과 |
| 가입·재설정 IP 제한 | `login-throttle.ts:153` | 항상 통과 |
| 제한 위반 기록 | `login-throttle.ts:73` | 기록조차 안 남음 |
| **관리자가 등록한 차단 IP 명단** | `ip-block.ts:24,35` | **차단 기능 자체가 죽음** |
| 접속기록의 IP 칸 | `access-log.ts` | 항상 빈칸(사고 조사 불가) |
| 에이전트 페어링 IP 차단 | `agent-auth.ts:52` | 항상 통과 |

**가장 위험한 것은 4번째 줄입니다.** 관리자가 [보안] → [차단 IP]에 공격자 IP를 등록하면
화면에는 "등록됨"으로 보이는데 **실제로는 아무 일도 하지 않습니다.**
"막고 있다"는 잘못된 확신을 주는 것이 기능이 없는 것보다 위험합니다.

#### 수정 방법

**(1) 배포 시 — 반드시 세 가지를 한 묶음으로**

`docs/08_security/TRUST_PROXY_운영주의_2026-08-03.md`에 이미 정확히 정리되어 있습니다.

```nginx
# ❌ 위험 — nginx 기본 관용구. 클라이언트가 보낸 값 뒤에 덧붙여서 맨 앞이 위조값이 된다.
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

# ✅ 안전 — 프록시가 직접 본 접속 IP로 덮어쓴다.
proxy_set_header X-Forwarded-For $remote_addr;
```

그 다음에야 `.env`에 `TRUST_PROXY=1`을 넣습니다.
⚠️ **프록시 없이 `TRUST_PROXY=1`만 켜면 정반대로 위험해집니다** — 접속자가 자기 IP를 마음대로 속일 수 있고,
그러면 사무실 IP 출근 위조·차단 IP 우회가 모두 성립합니다.

**(2) 코드 개선(다음 업데이트)**

- **화면에 상태를 표시한다** — [차단 IP] 화면 상단에 "현재 접속 IP를 읽을 수 없어 이 목록은 적용되지 않습니다"를
  띄운다. 잘못된 확신을 없애는 것이 이 항목의 핵심입니다.
- `X-Forwarded-For`를 **맨 앞이 아니라 "뒤에서 N번째"** 로 읽게 바꾸면 nginx 설정 실수까지 방어됩니다
  (위 문서의 "남은 개선 과제"에 이미 적혀 있음).

### H-5. 운영자(본사) 콘솔 보호가 비밀번호 1개뿐 — 2FA·IP 제한 없음

| 항목 | 내용 |
|---|---|
| **위험도** | **High** |
| **파일** | `webapp/app/actions/operator.ts`, `webapp/lib/operator-session.ts`, `webapp/proxy.ts:41-43`, `webapp/scripts/create-operator.mjs:52` |
| **기능** | `/operator` — 전 회원사를 보는 유일한 화면 |
| **우선순위** | **운영 전 수정 권장 (기능 확장 전 필수)** |

#### 문제 설명

운영자 계정은 **회사 칸막이를 넘어 전 회원사를 보는 유일한 열쇠**입니다.
현재 보호 수단은 다음이 전부입니다.

- 비밀번호 1요소 (최소 12자, **복잡도 요구 없음**)
- 5회/10분 계정 잠금
- 1분 30건 문 상한 — **프로세스 메모리**라 서버 재시작 시 초기화

**2FA(일회용 인증번호)·IP 허용목록·기기 등록이 코드에 전혀 없습니다.** `proxy.ts`는 쿠키가
"있는지"만 볼 뿐 유효한지는 보지 않습니다(이건 의도된 설계이고 주석에 이유가 정확히 적혀 있습니다).

또한 운영자는 비밀번호 재설정 창구가 **일부러 없어서**, H-1의 잠금 공격을 받으면
**서버 셸에서 `--unlock`을 실행하기 전까지 본사 관제가 완전히 마비**됩니다.

#### 완화 요인 (지금 당장은 덜 급한 이유)

현재 `/operator`는 **로그인 화면과 빈 페이지만 있는 껍데기**입니다. 회원사 목록·데이터 조회 화면이
아직 구현되지 않아 **지금 뚫려도 나갈 데이터가 없습니다.** 그래서 "기능을 붙이기 전에 먼저 잠그라"는
순서 문제입니다.

#### 수정 방법

1. **배포 체크리스트 6번을 반드시 이행** — 프록시에서 `/operator` 경로를 **사내 IP만 허용**.
   이것이 실질적인 본 방어선입니다. (`docs/09_test/배포전_체크리스트.md`에 이미 등재됨)
2. **회원사 데이터 조회 화면을 만들기 전에** 2FA(TOTP)를 먼저 붙인다.
3. 운영자가 **다른 회사 데이터를 열람한 기록**을 남기는 감사 함수를 추가한다.
   현재 `lib/audit.ts`의 `logAdminAction`은 회사 소속 사용자를 전제로 하고 있어
   "운영자가 A사를 열람했다"를 표현할 수 없습니다.
4. 운영자 계정을 **2개 이상** 만들어 둔다(하나가 잠겨도 들어갈 수 있게).

### M1 상세 — 고아 파일 누적 (가장 즉시 악용 가능)

```ts
// app/api/request-attachment/upload/route.ts:50-65
const saved = [];
try {
  for (const file of files) {
    if (file.size > MAX_SIZE) return NextResponse.json({...}, { status: 400 });  // ← ①
    const buffer = Buffer.from(await file.arrayBuffer());
    const mime = detectMime(buffer);
    if (!mime) return NextResponse.json({...}, { status: 400 });                 // ← ②
    const storedName = await saveAttachmentFile(me.companyId, buffer, mime);     // ← 디스크에 씀
    saved.push({ storedName, ... });
  }
} catch (e) {
  await Promise.all(saved.map((s) => deleteAttachmentFile(...)));   // ← 정리 코드
  ...
}
```

주석은 "하나라도 실패하면 되돌린다"고 적혀 있지만, **①②의 `return`은 `catch`를 발동시키지 않습니다.**
그래서 **이미 디스크에 쓴 파일이 정리되지 않고 그대로 남습니다.** DB 레코드도 안 생기므로
3년 자동 파기(`work-record-retention.ts`)도 이 파일을 **영원히 찾지 못합니다.**

**공격**: 로그인한 아무 직원이나 `[정상 PNG 10MB × 4] + [.txt 1개]`를 보내면 **40MB가 고아로 남습니다.**
개수 상한(5개)은 DB `count`를 보는데 DB 행이 안 생기므로 **무한 반복 가능**합니다. 25번이면 1GB.
업로드에 횟수 제한도 없습니다.

**수정**: `try` 안의 `return`들을 `throw`로 바꿔 `catch`의 정리 코드를 타게 하거나,
검증(크기·매직바이트)을 **전부 먼저 끝낸 뒤** 저장을 시작하는 2단계 구조로 바꿉니다.
후자가 더 안전합니다. 참고로 **DB 저장 실패 경로는 정리가 제대로 되어 있습니다**(`:88-89`) — 검증 실패 경로만 빠졌습니다.

### M16 상세 — 가입자 개인정보·비밀번호 해시가 서버 로그에 남을 수 있음

```ts
// app/actions/auth.ts:139-157 — 바로 위에서 email·phone·passwordHash로 계정을 만든다
const u = await tx.user.create({ data: { companyId, email, phone, passwordHash, ... } });
...
} catch (e) {
  console.warn("[signup] 회사 생성 실패:", e);   // ← 에러 객체를 통째로
```

같은 패턴이 `app/actions/invites.ts:135`(`console.error("[acceptInvite] 가입 실패", e)`)에도 있습니다.

**왜 문제인가**: Prisma의 검증 에러(`PrismaClientValidationError`)는 **에러 메시지 안에 전달한 데이터를
그대로 펼쳐 넣습니다.** 즉 서버 로그 파일에 가입자의 **이메일·전화번호·비밀번호 해시**가 남을 수 있습니다.

**근거 — 이 저장소가 이미 같은 함정을 알고 다른 곳에서는 고쳤습니다** (`lib/session.ts:121-122`):

> `// ⚠️ 에러 객체를 통째로 찍지 않는다 — Prisma 검증 에러는 인자(세션 토큰)를 펼쳐 넣는다(사규 8).`
> `console.warn("[session] ...", e instanceof Error ? e.message : String(e));`

**즉 규칙은 이미 정해져 있고 두 곳에만 적용이 안 된 것**입니다.

**피해**: 서버 로그를 볼 수 있는 사람(운영 협력사, 로그 수집 서비스, 유출된 로그 파일)이 가입자
개인정보와 비밀번호 해시를 얻습니다. 해시는 scrypt라 즉시 풀리지 않지만, **M4(해싱 강도 미달)와
M3(8자 정책)이 겹치면** 오프라인 대입의 출발점이 됩니다.

**수정** (2줄, 기존 패턴 그대로 복사):
```ts
console.warn("[signup] 회사 생성 실패:", e instanceof Error ? e.message : String(e));
```

## 5. 확인 결과 "문제 없음" — 증거

> 사장님 요청대로 "문제가 없어 보입니다"로 끝내지 않고, **무엇을 어떻게 확인했는지** 남깁니다.

### ✅ 1순위 — 회사 간 데이터 격리 / IDOR : **취약점 0건**

가장 중요한 항목이라 가장 오래 팠고, **제가 무작위 표본으로 교차검증까지 했습니다.**

- **점검 범위**: 서버액션 32개 파일 전수, 라우트 핸들러 17개 전수, 페이지 53개, 관련 lib 12개
- **핵심 확인**: `update({ where: { id } })` 패턴 89곳을 **전부 개별 추적**. 전부 아래 2단계 패턴이었습니다.

```ts
// 예: app/actions/employees.ts:98-106
const target = await prisma.user.findFirst({ where: { id, companyId: me.companyId } });  // ← 회사로 먼저 거름
if (!target) return { error: "직원을 찾을 수 없습니다." };
await prisma.user.update({ where: { id: target.id }, data: { name } });                   // ← 걸러진 결과의 id만 사용
```

`update`에 들어가는 `id`는 **폼에서 온 값이 아니라 회사로 걸러낸 조회 결과의 id**입니다.
제가 직접 무작위로 뽑은 `authmethod.ts:130`, `departments.ts:110`, `departments.ts:163` 3곳도
모두 `findFirst({ id, companyId })` 선행 검증이 있었습니다.

- **`companyId`를 사용자 입력에서 받는 곳: 0건.** 전수 검색 결과 모든 `companyId`는 세션 또는 기기 토큰에서만 옵니다.
  PC 에이전트 API는 명시적으로 방어합니다 — `app/api/agent/events/route.ts:108`:
  `companyId: auth.user.companyId, // 앱이 보낸 값은 믿지 않는다`
- **엑셀 4개 경로 전부** `role !== "admin"` 차단 + `companyId` 스코프.
- **URL 파라미터 상세 화면 3개** 전부 `findFirst({ id, companyId })` + `notFound()`.
- **파일 다운로드 4개 전부** 회사 격리 — 제가 직접 `clock-photo`·`company-doc`·`request-attachment` 코드를 읽어 확인했습니다.

### ✅ SQL 인젝션 : **구조적으로 불가**

`$queryRaw`·`$executeRaw`·`$queryRawUnsafe`·`$executeRawUnsafe` **검색 결과 0건.**
모든 DB 접근이 Prisma를 거치며 값은 파라미터로 바인딩됩니다. 정렬·필터를 문자열로 조립하는 곳도 없습니다
(`lib/search.ts`는 DB에 접근하지 않는 순수 메모리 필터).

### ✅ 파일 업로드 — 저장형 XSS · Path Traversal : **불가**

- **확장자가 아니라 실제 파일 앞부분 바이트로 판별** (`lib/company-doc.ts:30-39`) — PDF(`%PDF`)·PNG·JPEG 3종만 통과.
  클라이언트가 신고한 MIME(`file.type`)과 확장자는 **아예 보지 않습니다.**
- HTML·SVG·JS·EXE·PHP는 업로드 단계에서 차단됩니다.
- **저장 파일명은 100% 서버가 난수로 생성** (`${Date.now()}-${randomBytes(12).hex}.${ext}`),
  읽을 때도 `/^[0-9a-f-]+\.(pdf|jpg|png)$/i`로 재검증 → Path Traversal 불가.
- 사용자 파일명은 표시용으로만 쓰이고 `encodeURIComponent`로 인코딩 → 헤더 인젝션도 차단.
- **저장 위치가 `public/`이 아니라 `storage/`** — 웹에서 직접 접근 불가. `public/`에는 정적 이미지만 있습니다(직접 확인).
- 다운로드 시 `Content-Type`은 **DB에 저장된 서버 판별값**이고 `X-Content-Type-Options: nosniff`가 붙습니다.

### ✅ 생체정보(얼굴사진) 보호

- **AES-256-GCM 실제 구현** (`lib/clock-photo.ts:26,50-62`). 키는 환경변수에서만 읽고 64자리 hex를 강제. 하드코딩 없음.
  GCM이라 변조 탐지까지 됩니다.
- 열람 라우트가 **5중 방어**: 로그인 → 관리자 → 회사격리 → **판정상태 화이트리스트** → 90일 만료.
  특히 "정상 확인된 사진은 관리자도 못 본다"는 최소열람 원칙이 화이트리스트(`suspect`·`error`만 허용)로 구현되어
  있고, 상태값이 늘어나도 자동으로 막히는 방향(fail-safe)입니다.
- **얼굴 특징값은 우리 DB에 없습니다** — `User`에 등록 시각·횟수 표시만 있고 임베딩·이미지 컬럼이 없습니다.
- 삭제 경로 3개(본인 철회·GPS 전환·관리자 파기) 모두 **얼굴서버 원본을 먼저 지우고 DB를 나중에** 갱신 — 순서가 정확합니다.

### ✅ 권한 상승(Mass Assignment) : **0건**

- `Object.fromEntries(formData)` 사용 **0건**.
- `role`·`isOwner`·`companyId`를 `formData`에서 읽는 곳 **0건**(전수 검색).
- 직원 프로필 수정은 `phone`·`employeeNo`·`hireDate`·`jobGradeId`만 쓰고,
  그 `jobGradeId`조차 회사 소속인지 재검증합니다(`employees.ts:147-151`).
- **일반 직원이 `role=admin`을 넣어 관리자가 되는 경로는 없습니다.**

## 6. 검수의 한계 — 오탐 정정과 확인 못 한 영역

### 6-A. 검수 중 "치명"으로 제기됐다가 **오탐으로 판명된 건** — 긴급 대응 불필요

검수 과정에서 **"얼굴서버 라이선스 키 실제 값이 GitHub에 올라갔다 → 즉시 키 재발급 필요"**라는
Critical 지적이 제기됐습니다. **검증 결과 사실이 아닙니다.** 사장님이 불필요한 긴급 대응을 하지
않으시도록, 그리고 나중에 같은 지적이 또 나오지 않도록 근거를 남깁니다.

**무슨 일이 있었나**: `.env`의 `FACE_LICENSE_KEY` 값을 검색했더니 `PROGRESS.md`에서 발견됐고,
"비밀키가 문서에 유출됐다"로 판단된 것입니다.

**검증 방법과 결과** (값을 화면에 찍지 않고 문자열 일치만 비교):

| 확인 | 결과 |
|---|---|
| `.env`의 `FACE_LICENSE_KEY` 실제 값 | 문자 그대로 **`GAON_TEST_LICENSE`** (17자) |
| `.env`의 `FACE_CLIENT_ID` 실제 값 | 문자 그대로 **`GAON_TEST_CLIENT`** (16자) |
| `FACE_CLIENT_SECRET` 값이 git 추적 파일에 | **0건** |
| `FACE_CLIENT_SECRET` 값이 git 히스토리 전체에 | **0건** |

즉 문서에 적힌 것은 **무작위 비밀키가 아니라 공개 테스트계정의 표시용 이름**입니다.
`docs`와 커밋 메시지가 원래부터 "**공개** 테스트계정"이라고 밝히고 있었고, 진짜 비밀에 해당하는
`FACE_CLIENT_SECRET`은 **`.env`에만 있으며 단 한 번도 커밋된 적이 없습니다.**

**결론**: 키 재발급 같은 긴급 조치는 **필요 없습니다.** 실서비스 전 운영 계정으로 교체하는
기존 절차(배포 체크리스트 5번)만 지키면 됩니다. 위 L11로 등급을 낮춰 기록합니다.

> 이 건을 굳이 남기는 이유: 보안 검수에서 "값이 문서에서 발견됐다"는 사실만으로 비밀 유출로
> 단정하면, 진짜 급한 일(C-1)에 쓸 시간을 엉뚱한 데 씁니다. **값이 실제로 비밀인지 먼저 확인**해야 합니다.
