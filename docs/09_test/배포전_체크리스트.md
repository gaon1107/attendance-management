### 2. 운영은 개발 서버(`npm run dev`)로 띄우지 않는다
- `근태관리_실행.bat`은 **사장님 PC 개발·테스트 전용**이다.
- 운영은 `npm run build` → `npm run start`(`NODE_ENV=production`)로 띄워야 한다.
- 이유: dev 모드에서는 **세션 쿠키에 `Secure` 표시가 붙지 않고**, 오류 발생 시 내부 파일 경로·소스가 브라우저에 그대로 노출된다.
- (검수 H-3 — 5순위에서 실행 스크립트 분리 예정)

### 2-1. 프록시에서 `/login` 캐시 금지 (2026-08-11 추가)
로그인 화면이 **로그인한 사람의 실명**을 담게 됐다(다른 계정으로 갈아탈 때 뜨는 경고 배너 — 검수 M-15).
공용 캐시가 이 화면을 저장하면 **A의 이름이 든 화면이 B에게 나갈 수 있다**(사무실 하나가 공인 IP·프록시를
함께 쓰는 중소기업이 타겟이라 가정이 아니다).

- **조치**: 리버스 프록시(Nginx 등)에서 `/login`에 `Cache-Control: private, no-store`를 강제한다.
  ```
  location = /login { proxy_pass http://app; add_header Cache-Control "private, no-store" always; }
  ```
- ⚠️ **앱 코드로는 못 막는다.** `next.config.ts`의 `headers()`에 넣어도 Next가 동적 페이지의
  `Cache-Control`을 자기 값(`no-cache, must-revalidate`)으로 덮어쓴다(실측 확인). 다른 헤더는 정상 적용된다.
- 현재값(`no-cache, must-revalidate`)도 규격을 지키는 캐시라면 **매번 서버에 확인**하므로 남의 화면이
  그대로 나가지는 않는다. 위 조치는 "저장 자체를 막는" 한 겹 더다.
- **배포 후 확인**: `curl -sI https://<주소>/login | grep -i cache-control` → `private, no-store` 확인.

### 3. HTTPS + 리버스 프록시 + `TRUST_PROXY=1` (셋이 한 묶음)
- 접속 IP를 신뢰하려면 앞단에 프록시(Nginx/IIS)가 반드시 있어야 한다.
- 프록시 없이 접속자가 보낸 IP 헤더를 믿으면 **자기 IP를 마음대로 속일 수 있어** 사무실 IP 출근 인증·차단 IP가 무력화된다.
- **코드는 이미 대응됨(2026-08-02, 검수 H-1)**: 기본값은 "헤더를 믿지 않음"이다.
  - 그래서 지금은 사무실 IP 판정이 항상 **"확인 불가"** 로 나오고, 접속기록의 IP 칸도 비어 있다. 정상이다.
  - 프록시를 세운 뒤 `.env`에 **`TRUST_PROXY=1`** 을 넣어야 사무실 IP 인증·IP 차단·접속기록 IP가 다시 작동한다.
  - ⚠️ 프록시 없이 `TRUST_PROXY=1`을 켜면 안 된다 — 위조를 그대로 믿게 된다.

### 3-2. 프록시에서 로그인·가입·재설정 경로에 **요청 수 제한**을 건다 (검수 C-1, 2026-08-30 추가)
- 코드 안에도 분당 상한이 들어갔다(`webapp/lib/public-door.ts`). 로그인 600 / 가입 60 / 재설정 120건.
  이건 **서버가 죽는 것을 막는 최후의 안전판**이지, 진짜 방어선이 아니다.
- **진짜 방어선은 프록시(Nginx 등)의 요청 수 제한**이다. 코드 상한은 요청이 우리 서버까지 들어온 뒤에
  세는 것이라, 폭주하면 네트워크와 프록시는 이미 부담을 받는다.
- 🔴 **경로(`/login` 등)로 규칙을 걸면 새어 나간다.** 이 앱의 로그인·가입·재설정은 화면(URL)이 아니라
  **서버 액션**이라, 어느 주소로 보내도 `Next-Action` 헤더에 적힌 동작이 실행된다.
  `/login`만 막으면 공격자가 `/` 로 보내 그대로 통과한다.
  - **규칙은 "`Next-Action` 헤더가 붙은 POST 전체"** 에 건다. 또는 POST 전체에 걸고
    파일 업로드 경로(얼굴 사진 등)만 예외로 둔다.
  - 권장: IP당 분당 30건 정도. 사무실이 한 공인 IP를 함께 써도 넉넉하다.
  - ⚠️ 배포 전에 `curl`로 한 번 확인할 것 — 로그인 화면의 `Next-Action` 값을 그대로 `/` 로 POST해
    응답이 오면 경로 기반 규칙은 무용지물이라는 뜻이다.
- **요청 본문 크기 제한도 프록시에서 건다.** 서버 액션 본문 한도가 4MB(얼굴 사진 때문)라,
  코드 상한은 **본문을 다 받은 뒤에야** 걸린다. 대역폭 소모는 프록시에서만 막을 수 있다.
- ⚠️ **코드 상한은 "프로세스당" 상한이다.** 서버를 여러 대로 늘릴 때뿐 아니라
  **한 대라도 PM2 cluster·IIS(iisnode) 워커를 여러 개 띄우면 워커 수만큼 상한이 곱해진다.**
  그때는 프록시나 Redis 같은 공용 저장소로 옮겨야 한다.
- 정상 사용자가 상한에 걸리고 있는지는 **서버 로그의 `[public-door]` 줄**로 확인한다.
  걸린다면 `.env`에서 `LOGIN_DOOR_MAX_PER_MIN` 등을 올리고 서버를 재시작한다(`0`이면 상한 해제).
- 🔴 **서버 로그를 반드시 파일로 남길 것.** 지금 개발용 실행 방식(`근태관리_실행.bat`)은 콘솔 창에만 찍고
  창을 닫으면 사라진다. 문에 걸린 요청은 (적재 공격을 막으려고) DB 접속기록에도 남기지 않으므로,
  **로그 파일이 없으면 "아침에 직원들이 로그인을 못 했다"는 신고가 들어와도 증거가 하나도 없다.**

### 3-3. `UV_THREADPOOL_SIZE` — 로그인이 몰리는 규모라면 (검수 C-1, 2026-08-30 추가)
- 비밀번호 계산은 이제 **별도 작업 스레드**에서 돈다(서버 본체가 멈추지 않는다). 그 스레드는 **기본 4개**다.
- 직원 수가 많아 아침에 로그인이 몰리면(회사 100곳·직원 10,000명 규모) 스레드를 CPU 코어 수에 맞춰 올린다.
  - 설정 위치: **서버 실행 환경변수**(`.env`가 아니라 서비스/PM2/IIS 설정). 예: `UV_THREADPOOL_SIZE=8`
  - 코어 수보다 크게 잡을 이유는 없다. **비밀번호 계산 1회가 약 16MB를 쓰므로**
    스레드 수 × 16MB가 순간 메모리다(64로 잡으면 1GB가 순간적으로 잡힌다).
  - 잘 모르면 **손대지 않아도 된다**(기본 4로도 분당 약 6,000건을 처리한다).
  - ⚠️ 이 값을 올렸다면 `.env`의 `LOGIN_DOOR_MAX_PER_MIN`(코드 기본 3,000)도 함께 올릴 수 있다.
    그 값은 "스레드 4개 = 분당 6,000건"의 절반을 기준으로 정한 것이다.

### 3-1. 임시 비밀번호는 48시간 만료 (검수 H-4, 2026-08-02 적용)
- 관리자가 발급한 임시 비밀번호는 48시간이 지나면 로그인에 쓸 수 없다. 지나면 직원이 재설정을 다시 요청하면 된다.
- 임시 비밀번호로 로그인하면 **모든 화면이 막히고** 새 비밀번호 설정 화면으로 보내진다(예전엔 주소창으로 우회 가능했다).

### 4. 사진 암호화 키(`CLOCK_PHOTO_KEY`) 백업
- `.env`의 이 키를 잃어버리면 저장된 출퇴근 사진을 **영원히 복호화할 수 없다**.
- 운영 이전 시 키를 안전한 곳에 별도 보관한다.

### 5. 얼굴인식 운영 전환
- 현재는 개발 얼굴서버(`gaonfrdev`) + 공개 테스트 계정을 쓰고 있다.
- 실서비스 전 **운영서버에 근태 전용 클라이언트 신규 발급 + 직원 동의 + 위수탁 계약**이 필요하다.

### 6. 운영자(본사) 백오피스 `/operator` — 열쇠 만들기 + 접근 제한 (2026-08-18 신설)
`/operator`는 **회사 칸막이를 넘어 전 회원사를 보는 유일한 화면**이다. 그래서 순서가 있다.

- [ ] **운영자 계정 만들기.** 지금 DB에는 계정이 **0건**이다(문은 있지만 열쇠가 없는 상태).
  ```powershell
  cd webapp ; node scripts/create-operator.mjs "이메일" "비밀번호(12자 이상)" "이름"
  ```
  - 비밀번호는 **12자 이상**(전 회원사를 보는 계정이라 고객사 8자보다 높게 잡았다). 통문장 권장.
  - ⚠️ 비밀번호가 **PowerShell 명령 기록에 남는다.** 만든 뒤 `Clear-History` 로 지우거나, 남아도 되는 PC에서 실행한다.
  - 계정 확인 `--list` / 잠금 풀기 `--unlock "이메일"` / 비번 변경 `--reset "이메일" "새 비번"` / 끄기·켜기 `--off`·`--on`
- [ ] **프록시에서 `/operator` 경로를 사내 IP만 허용.** 이게 이 문의 실질적인 방어선이다.
  - 이유: 위 3번(`TRUST_PROXY=1`)을 켜기 전까지 IP 단위 시도 제한은 **아무 일도 하지 않는다.**
    그 상태에서 이 문에 로그인 요청을 쏟으면 요청마다 비밀번호 계산(약 40ms, 그 동안 **서버 전체가 멈춤**)이
    돌아 **직원들이 출퇴근을 못 찍을 수 있다.**
  - 코드에도 임시 방벽을 뒀다(1분 30건, `lib/operator-policy.ts`). 다만 서버를 여러 대로 늘리면 대당 상한이 되므로
    **프록시 제한이 본 방어이고 코드 상한은 보조**다.
- [ ] **계정 잠금 시 복구 경로를 알고 있는가.** 운영자에게는 비밀번호 찾기·재설정 화면이 **일부러 없다.**
  잊거나 잠기면 서버에서 위 명령으로만 푼다. 서버 접근 수단(원격 데스크톱 등)을 미리 확인해 둘 것.
- [ ] 운영자 계정을 **2개 이상** 만들어 둘 것 권장 — 하나가 잠겨도 다른 하나로 들어갈 수 있다.
