## 0. 한 줄 요약

기존 단일 사진 라이브니스가 **오려낸 인쇄 사진·휴대폰 화면 공격에 뚫리고, 저조도에서 진짜를 오탐**하던 문제를,
**연속 3장 판정 + 모델별 차등 기준 + 얼굴크기/밝기 게이트**로 해결했다. 판독 AI·전처리는 그대로 두고 **판정 로직과 전·후처리만** 보강했으므로, 아래 모듈을 이식하고 설정값을 적용하면 된다.

## 1. 개선 항목 요약

| # | 개선 | 무엇을 | 효과 (실측) | 상태 |
|---|------|--------|------------|------|
| 1 | **연속 3장 촬영·전 장 통과** | 촬영 1회에 0.3초 간격 3장 → 모든 장이 통과해야 진짜 | 각도 운으로 한 장만 통과하던 오려낸 사진 차단 | ✅ 확정 |
| 2 | **모델별 차등 판정** | 모델 A(V1SE)·B(V2)에 다른 기준(A 낮게/B 높게) | 저조도 진짜 오탐 해결 + 위조 차단 유지 | ✅ 확정(핵심) |
| 3 | **얼굴 최소 크기 게이트** | 화면 대비 얼굴 폭 % 미만이면 판독 안 함·재촬영 안내 | 작은 얼굴 저품질 판독 방지 (기존 기능 유지) | ✅ 확정 |
| 4 | **밝기 게이트** | 얼굴이 너무 어두우면 판독 대신 "더 밝은 곳" 안내 | 캄캄한 조건의 오탐을 재촬영으로 전환 | 🟡 기준값 검증 중(80 테스트) |
| 5 | **동일 사진 반복 거절** | 3장이 바이트 동일하면 거절 | 정지 이미지 주입·가상 카메라·카메라 멈춤 차단 | ✅ 확정 |
| 6 | 질감(망점·모아레) FFT 검사 | 얼굴 질감 규칙무늬 점수 | **효과 없음 확정**(진짜/위조 겹침) → 판정 미반영 | ⚪ 관찰용 존치·이식 선택 |

**실측 근거(요약)**
- 오려낸 인쇄 사진: 여러 각도·구부림에도 위조 의심 판정(예전 84.7% 통과 → 차단).
- 휴대폰 화면: 모델 A·B **둘 다 0.0%** → 완전 차단(밝기 104~125에서도).
- 저조도 진짜: 모델 A가 64~77%로 떨어져도 모델 B가 93%+ 유지 → 차등(A≥60·B≥85)으로 통과. 단일 기준 80%였다면 오탐.
- **핵심 원리**: 진짜 얼굴은 모델 B(V2) ≥ 약 93%, 위조는 모델 B ≤ 약 60%로 크게 갈림. 모델 B가 실질 판별자, 모델 A는 저조도에 약함.

## 2. 확정·권장 설정값

| 설정 | 권장값 | 범위/단위 | 비고 |
|------|--------|-----------|------|
| 연속 촬영 장수 | **3** | 1~3 | 0.3초 간격 |
| 판정 방식 | **모델별 차등** | 평균 / AND / 차등 | 아래 A·B 기준 사용 |
| 모델 A(V1SE) 기준 | **0.60 (60%)** | 0~1 | 저조도에 약해 낮게. 여유 원하면 0.50~0.55 |
| 모델 B(V2) 기준 | **0.85 (85%)** | 0~1 | 실질 판별자. 진짜 93%+ / 위조 60%- 사이 안전지대 |
| 전 장 통과 | **모든 장이 A·B 기준 통과** | — | 한 장이라도 미달이면 위조 의심 |
| 얼굴 최소 크기 | **35%** | 10~50% | 화면(4:3) 보이는 폭 대비 얼굴 폭 % |
| 밝기 기준 | **80** (검증 중) | 0~255, 0=끄기 | 얼굴 영역 평균 밝기. 현장 실측으로 최종화 |
| 동일 사진 거절 | **켬** | — | 바이트 동일 3장 거절 |
| 질감 검사 | **판정 미반영** | — | 관찰용. 이식 선택 |

> ⚠️ **밝기 기준(80)과 모니터·동영상 공격은 아직 최종 검증 전.** 근태 현장 카메라·조명이 데모와 다르면 밝기 기준을 재측정해야 한다(0=끄기로 두고 값만 관찰 → 어두운 진짜가 안 걸릴 최저선으로 설정). 모델 A/B 기준도 현장에서 진짜 통과·위조 차단을 재확인 권장.

## 3. 판정 파이프라인 (처리 순서)

```
촬영(연속 3장)
  │  각 장: 웹캠 원본 해상도(최대 폭 1280) JPEG, 850KB 이하로 재압축
  ▼
[서버] 입력 검증 (장수 1~3, 장당 900KB 이하)
  ▼
[서버] 동일 사진 반복 거절 (바이트 동일 → 거절)
  ▼
[서버] 얼굴 검출 (GaonFR detect) — 첫 장에서 1회만, 좌표를 3장에 재사용 (※429 회피)
  ▼
[서버] 얼굴 크기 게이트 — facePercent < minPercent → tooSmall(재촬영 안내)
  ▼
[서버] 밝기 게이트 — brightness < minBrightness → tooDark(재촬영 안내)  ※minBrightness=0이면 건너뜀
  ▼
[서버] 장별 판독 — 각 장 analyzeFace(MiniFASNet V1SE/V2) → 모델 A/B 진짜확률
  │        (+ 질감 점수 = 관찰용, 판정 미반영)
  ▼
[판정] 모든 장이 (모델A ≥ 기준A) 그리고 (모델B ≥ 기준B) → 진짜, 아니면 위조 의심
```

- **얼굴 폭 % 계산**(근태와 동일): `visibleWidth = min(imgW, imgH*4/3); facePercent = rect.width / visibleWidth * 100`
- **검출 1회 재사용 이유**: GaonFR 얼굴서버가 짧은 간격 연속 detect에 **429(요청 폭주)** 를 반환하는 것을 실측. 장 간격 0.3초라 얼굴 이동 미미하고, 판독 크롭이 4.0/2.7배로 넓어 좌표 오차에 관대.

## 4. 이식할 파일

### 4-1. 그대로 복사 가능한 순수 모듈 (`lib/`)
| 파일 | 역할 | 의존성 | 이식 |
|------|------|--------|------|
| `lib/liveness.ts` | 판독 AI(MiniFASNet V1SE/V2) 로드·전처리·점수. `analyzeFace(buffer, rect)` | `onnxruntime-node`, `sharp`, 모델 2개 | **그대로** |
| `lib/gaonfr.ts` | GaonFR 얼굴서버 연동(토큰 2단계, detect). 근태 `lib/face.ts`와 동일 토큰 흐름 | `.env FACE_*` | 근태 기존 것과 통합 |
| `lib/quality.ts` | 얼굴 영역 평균 밝기 `faceBrightness(buffer, rect)` | `sharp` | **그대로** |
| `lib/texture.ts` | 질감 FFT 점수(관찰용) | `sharp` | 선택(판정 미반영) |
| `models/MiniFASNetV1SE.onnx`, `models/MiniFASNetV2.onnx` | 학습된 AI 두뇌(각 ~3.4MB, Apache-2.0) | — | **그대로**(경로: `webapp/models/` 후보 이미 코드에 있음) |

- `lib/liveness.ts`의 모델 경로 탐색 후보에 `webapp/models/`가 이미 포함되어 있어, 근태(webapp)에 `models/`를 두면 자동 인식.

### 4-2. 근태 구조에 맞춰 이식할 로직
| 소스 | 역할 | 근태 적용 |
|------|------|-----------|
| `app/actions/liveness.ts` | 서버 파이프라인(입력검증→동일거절→검출→크기→밝기→장별판독→반환) | 근태 출퇴근 서버 로직에 이식. 프레임 배열 입력·게이트·판독 순서 그대로 |
| `app/DemoClient.tsx`의 판정부 | 연속 촬영·판정(차등)·재판정 | 아래 4-3 판정식만 이식(데모 UI/슬라이더는 불필요) |
| `next.config.ts` | 서버 액션 본문 한도 4MB(3장 전송) | 근태 전송 방식에 맞게 반영 |

### 4-3. 판정 로직 (핵심 — 그대로 옮길 것)
```ts
// 장별 통과 여부 (권장: 모델별 차등)
const framePass = (v1se, v2) => (v1se >= thA && v2 >= thB);   // 권장 thA=0.60, thB=0.85
// 촬영 통과 = 모든 장이 통과
const capturePass = (frames) => frames.length > 0 && frames.every(f => framePass(f.v1se, f.v2));
// 최종: capturePass면 진짜, 아니면 위조 의심
```
> 참고: 데모에는 평균/AND 방식도 있으나(호환·비교용), **근태는 차등만** 쓰면 된다.

> 🔐 **보안 권장**: 데모는 라이브 슬라이더 튜닝을 위해 **판정을 화면(클라이언트)** 에서 한다. 근태 운영은 **판정을 서버에서** 수행할 것(클라이언트는 점수 조작 가능). 서버 액션이 모델 A/B 점수를 이미 가지고 있으므로, 위 `framePass/capturePass`를 서버에서 실행하고 결과만 내려주면 된다.

## 5. 🚫 절대 바꾸면 안 되는 것 (판독 점수에 직접 영향)

`lib/liveness.ts`의 전처리 상수 — **바꾸면 점수가 최대 12%p 흔들리고, 위 기준값이 전부 무효가 된다.**
- 크롭 확장 배율: **V1SE = 4.0, V2 = 2.7**
- 입력 크기: **80 × 80**
- 리사이즈 커널: **linear** (원 구현 cv2.INTER_LINEAR 재현)
- 색 순서·정규화: **BGR, 0~255 float, 정규화 없음**
- 출력 해석: softmax 3클래스 중 **[1] = 진짜(Real) 확률**

기준값(모델 A/B, 밝기)은 반드시 **이 전처리 그대로**에서 현장 실측으로 확정할 것.

## 6. 성능·제약

- **속도**: 검출 약 60~120ms + 판독 3장 합계 약 120~250ms(첫 장 190ms + 2·3장 각 20~30ms, 모델 캐시 후). 총 0.3~0.4초 수준.
- **GaonFR 429**: 짧은 간격 연속 detect 금지 → 촬영당 detect 1회 원칙 유지.
- **서버 액션 본문 한도**: 기본 1MB → 3장 전송 위해 4MB로 상향(`next.config.ts`). 근태 전송 경로에 맞게 반영.
- **사진 저장 안 함**: 판독 후 메모리에서 폐기.
- **의존성**: `onnxruntime-node ^1.20`, `sharp ^0.34`, Next 16 / React 19 (데모 기준).
- **.env 키**: `FACE_API_BASE_URL`, `FACE_CLIENT_ID`, `FACE_CLIENT_SECRET`, `FACE_LICENSE_KEY` (비밀값은 코드에 두지 말 것).

## 7. 검증 방법 (재현 스크립트)

프로젝트 루트에서:
- `npx tsc --noEmit` — 타입 검사
- `npx -y tsx scripts/multiframe-test.ts` — 서버 5경로(3장/1장/4장 거절/크기 미달/동일사진 거절)
- `npx -y tsx scripts/brightness-test.ts` — 밝기 측정·tooDark 경로

라이브 확인: `npm run dev`(데모 포트 3100) → 웹캠으로 본인/오려낸 사진/휴대폰 화면/모니터/동영상 테스트, 이력 표의 모델 A/B·밝기·판정 비교.

## 8. 미검증·남은 일 (이식 전 확인 권장)

1. **모니터·동영상 공격 미검증** — 휴대폰 화면은 완전 차단(모델 0%) 확인. 큰 모니터·동영상 재생은 미확인(화면이 커서 모아레가 덜 잡힐 수 있음). 근태 도입 전 확인 권장.
2. **밝기 기준(80) 최종화** — 데모 환경 값. 근태 현장 카메라·조명에서 재측정 필요.
3. **모델 A/B 기준(60/85) 현장 재확인** — 진짜 통과·위조 차단을 근태 카메라로 재검증.
4. **근본 대책**: 출퇴근 단말기 옆 **조명 확보**가 저조도 문제의 가장 확실한 해결책(소프트웨어는 보조).
5. **판정 서버화**(4-3 보안 권장) — 운영은 서버 판정.
6. **학습(훈련)용 원본 소스 백업** — 모델 재학습·튜닝이 필요할 때 대비(Apache-2.0 공개 저장소, 소실 대비).
